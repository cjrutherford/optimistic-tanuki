The harness scores schema conformance, question distinctness across five different people (the exact failure being fixed — a model that collapses to one question reintroduces it), grounding in the person's own work, self-report avoidance, whether it honours remaining-quadrant instructions, assessment sanity, and median latency. risks & decisions

Risks

  • Local model reliability. Handled. Both onboarding-analysis.service and application-generation.service fall back to deterministic output when Ollama is unreachable or returns unusable JSON, so the interview and the generator degrade instead of stalling. Exercised by the unit suites, which run with no Ollama present.
  • Fabrication is the load-bearing risk in E. A resume generator that invents employment is worse than none. The subset assertion in E8 is the gate, not a nice-to-have.
  • ATS sources need a company list. Resolved. ats-company-lookup.service resolves board tokens and ats-company-suggestion.service proposes companies from the onboarding interview and lead interactions, so the user is never asked to supply a raw token.
  • Removing sources changes live topics. Resolved by 1787184267302-migrate-topics-off-retired-sources, which moves live topics off the retired providers rather than leaving them pointing at deleted code.
  • Unmigrated schema drift in lead-tracker. Resolved. The FK rewrite was fixed at the entity (restoring ON DELETE CASCADE on lead_qualifications.leadId) and landed as its own AlignLeadQualificationConstraints migration. migration:generate now reports no schema changes.
  • lead-tracker mixes two migration timestamp styles. Fixed — this was a hard blocker, not a style nit. A fresh database could not be built at all: AddOnboardingDiscTranscript sorted ahead of the migration that creates lead_onboarding_profiles and died on relation "lead_onboarding_profiles" does not exist. Every existing database already had the old migrations applied, so nothing failed locally — only CI and a new developer would have hit it. The whole directory now uses CLI epoch timestamps: the seven hand-numbered migrations moved to real epoch-ms values for the dates they were written, and the eight generated ones kept what the CLI assigned them. Run order matches authoring order, and migration:generate output can be committed as-is — no renaming step, and so no deviation from AGENTS.md's "do not hand-create migration timestamps". A fresh database applies all 21 in order with no drift against the entities. Enforced by validate-typeorm-migrations.mjs in CI, which detects hand-written dates by shape rather than magnitude — as an epoch value 2026090100000 is only the year 2034, so an upper bound missed it entirely.
  • Do not run a bare nx build while the dev stack is up. It writes the production bundle over what the containers serve, and nodemon does not recover from the gap — the service stays down with Cannot find module … main.js until restarted. Use --configuration=development, then restart the affected containers.

Review response

PR #235 · 2026-08-20

  • Presence gaps were fabricated on every Google result. The review flagged that findPresenceGaps treated undefined as a confirmed absence, contradicting the contract its own doc comment stated. The cause ran deeper: the provider queries Text Search, which never returns website, formatted_phone_number or full opening_hours — those are Place Details fields. So the mapping did not occasionally collapse an unknown; it fired on every result, stamping "No website listed" (40) and "No phone number listed" (10) on every lead and writing invented findings into the pitch text. Fixed by making the data real rather than only the mapping cautious: a bounded Place Details lookup (maxDetailLookups, default 25, since Details is billed per call) now establishes those fields, and anything it cannot answer stays unknown. The specs returned website on the search result and so could never have caught this; they now split search and details fields honestly.
  • Concurrent generates could share a version. lead_applications indexed (profileId, leadId, version) without uniqueness, and the next version was read before a slow LLM call — wide enough for a double-click. The index is now unique. Rather than hold a transaction across the generation, the service catches the unique violation (23505), re-reads the version and stores the documents it already produced, so a collision costs a retry of the insert rather than of the generation.
  • An unlabelled control. The remove-company chip button was a bare ×; it now carries an aria-label naming the company, with the glyph aria-hidden.
  • CI was red for an unrelated reason. payments/offer.service.spec.ts hardcoded expiresAt: 2026-08-16, so from the 17th the fixture was an already-expired offer and the suite failed on any branch — it fails identically on main. The first fix then introduced a subtler bug: sampling Date.now() inside the builder made it non-deterministic, and several tests call it twice, so two calls straddling a millisecond stopped being toEqual. One run passed by luck before the next failed elsewhere. Sampled once per run, and verified across repeated runs rather than a single green.
