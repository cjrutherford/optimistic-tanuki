# J17 — Bind Presence mutations to authenticated account

Use the authenticated account UUID from Gateway AuthGuard/@User for Presence writes. Ignore legacy POST body userId, preserving the client's old profile-ID fallback surface while deriving the actual actor on the server. For last-seen/offline route mutations, require the path UUID to equal that authenticated account, case-insensitively; reject a conflicting path with 403 before Social RPC. Missing/malformed principal fails with 401. Do not use selected profile claims as account ownership evidence.

Scope is Gateway PresenceController and a focused regression; root owns actual authenticated HTTP/Auth/Social/database evidence and release documents. Preserve HTTP route/body/status shapes, response contracts and cross-account reads/batch used by chat. Selected-profile session binding is J18, analytics J19 and Presence audience/privacy J20. No schema, UI or client change is needed here.

Prove the regression first, then run the narrow Nx tests and Gateway production build/lint before runtime. A private integration must use real Auth token/session validation and Social database writes through the actual controller, covering bearer and cookie credentials, malicious body/path IDs, a mismatched selected-profile claim, own mutations, missing credentials and exact counterpart readback/cleanup. A small HTTP harness may host the production controller and guard; record its composition and do not call it full Gateway deployment acceptance. Root reviews the source and evidence. Use a private labeled project and synthetic configuration only.
