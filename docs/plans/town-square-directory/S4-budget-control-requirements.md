# S4 provider budget controls — requirements

The user set a $25-per-month ceiling shared across **all providers and retries**. Every billed request counts. The prior decision not to acquire real source records yet still applies; setting a budget does not approve a provider, data use or rollout. No cost-control implementation or provider-side hard cap is established by this document.

Before any paid operation, determine the billing period and currency, actual provider rates and minimum charges, transfer/storage charges, free-tier interaction, taxes and rounding, and whether the provider exposes enforceable account-level caps. Treat unknown costs or an unavailable accounting authority as blocked rather than assume a request is free. The prior $20 alert was a proposal, not a replacement for the $25 limit.

A candidate implementation must use one durable shared ledger, rather than a separate $25 limit per provider or per worker. Atomically reserve a conservative upper bound for each billable request before it is sent; concurrent workers and retries draw from the same remaining allowance. Charge every retry separately, including requests that time out or fail if the provider might bill them. Record provider, operation, request identity, reservation, observed billing, time and outcome without secrets or unnecessary personal data. Make retries idempotent for accounting while preserving the distinction between a new billable attempt and a replay of an already recorded result.

When a request times out, crashes or has unknown billing outcome, retain the reservation until verified settlement or a deliberately conservative reconciliation. Never automatically release a reservation merely because a local process failed. If the potential total reaches $25, if the request has no reliable upper price, or if ledger/lock state is unavailable, stop further paid attempts and report a clear blocked reason. A local estimate cannot guarantee a hard financial cap where provider billing or currency, tax, overage, concurrent external use or delayed charges are not enforceable; use provider-side caps where available and identify any remaining exposure before activation.

Verification should include concurrent providers and workers, simultaneous reservations near the limit, retries, duplicate messages, process crash after provider dispatch, uncertain outcomes, failed persistence, calendar rollover, delayed charges, real reconciliation and provider-specific hard-stop behavior. No provider requests are needed for synthetic accounting tests. Actual billing limits and a production review must be established before claiming this ceiling is enforced.

## 2026-11-08 reservation foundation

`directory_provider_budget_attempt` and `reserveProviderBudget` implement a local shared reservation ledger with a $25 limit in whole US cents and a UTC calendar-month bucket. A transaction-scoped database lock serializes different providers, processes and retries sharing that database. Each billable attempt requires its own UUID and a known positive conservative maximum, rounded up to cents; unknown or zero maximums fail closed. An exact repeated attempt ID returns `replay`, which must never authorize another dispatch. Reservations are retained even after a crash or unknown outcome; no automatic release or settlement exists. A fresh disposable PostGIS test exercised concurrent providers near the cap, replay, changed IDs/costs and exhaustion.

This is not yet an enforced spending cap: the private range proxy can use the ledger through a required per-attempt reservation callback, but no trusted production wiring, price or billing reconciliation authority is configured, and UTC-month accounting has not been reconciled to individual provider billing periods. The ledger cannot constrain external account use, provider overage, taxes, delayed charges or requests dispatched across a period boundary. Provider-side limits, a dispatcher that refuses replay and checks period validity at dispatch, uncertainty reconciliation and real billing evidence remain required before paid requests or a hard-cap claim. It does not authorize acquisition.

The generated budget migration also adds database checks for a valid month and a reservation from 1 through 2,500 cents, plus a period index. Its down migration drops the ledger and therefore is **not** a safe production rollback while reservations or delayed charges exist; a recovery procedure must preserve and reconcile the ledger independently.

The range proxy requires a fresh reservation with the matching attempt ID and current UTC period before each upstream HEAD or GET; it rejects replays and explicit ranges that already exceed its remaining forwarded-byte limit. A synthetic database/proxy test reserves separately for a successful and failed request. Callbacks and price inputs are still caller assertions, open-ended or concurrent ranges can incur upstream egress before a response limit is known, and provider billing is not proven bounded.

## Signed authorization prototype

A synthetic Ed25519 grant verifier binds a short-lived authorization to a policy ID, exact asset URL hash, ETag, request method and positive maximum reservation. The ledger adapter verifies the signature against a separately supplied public key and locks an existing non-revoked policy while reserving; it checks the grant again after acquiring that lock. A disposable database and mocked proxy test covered source mismatch, a successful and a failed request, and denial after policy revocation. No provider request was made.

This remains a prototype, not an independent production authority: there is no trusted signer, key provisioning, authenticated policy approval, production dispatcher or database access control. A caller with direct database or proxy access can bypass this adapter. Revocation after reservation but before dispatch is an unresolved in-flight race, and the signed amount still needs independently verified prices and provider-side limits. These gaps must be closed before using it for real acquisition or claiming a hard spending cap.

The grant's subject is recorded as a signed identifier but is not yet tied to an authenticated caller. The adapter snapshots the token and request and revalidates after waiting for the policy and budget locks; this narrows expiry races but does not eliminate the post-reservation dispatch race. The Directory build, signed-grant unit test and disposable PostGIS budget/proxy test passed after integration. Migration validation also passed; this evidence does not establish a live billing control.

## Anonymous local Overture reads

The local October source path uses unsigned HTTPS requests to the pinned public Overture S3 object with `credentials: omit` and no authorization header. AWS documents that anonymous access is unavailable for Requester Pays buckets; these requests therefore do not charge an AWS requester account ([AWS S3 Requester Pays](https://docs.aws.amazon.com/AmazonS3/latest/userguide/RequesterPaysBuckets.html)). This does not establish the user's network or infrastructure costs.

The first October attempt conservatively reserved 1,224 cents in the paid-request ledger before failing its memory bound. Those are reservations, not observed charges; they are retained because the existing ledger has no verified settlement procedure. A separately signed, local-only anonymous receipt path now records unique free attempts without consuming the paid allowance, rejects replays across both receipt tables, checks policy revocation, and permits the free state only through the proxy's default anonymous transport. This is a local prototype: the signer is not independently provisioned, the callback itself is not an authenticated production authority, and its guarantees must not be generalized to paid or credentialed requests. The generated receipt migration's down path drops replay evidence and is not a safe production rollback.
