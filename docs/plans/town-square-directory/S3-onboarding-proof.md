## Update — 2026-11-06: pending register protocol

The later candidate uses retained dirty register entries, a source-incarnation-bound census and repair RPC, and generation-bound Directory sweeps rather than deleting entries or acknowledging the legacy stream. Explicit pending-only worker and Directory modes require an independently provisioned six-field identity and an operator assertion that the external fence is in place. That assertion cannot enforce the fence or detect an undisclosed restore. Legacy startup and ACK remain fenced. The older evidence and limitations below describe earlier prototypes and should not be interpreted as current production activation.

Focused checks on disposable databases and processes established:

- Checkpoint retry is exact, concurrent conflicting advances have one winner, stale generations and refenced authority are rejected, and corrupt sweep authority fails closed.
- A Social census catches a direct insert missing from the register; later sweeps also repaired direct privacy and name updates without a token change, and detected a direct deletion. A captured town behind a cursor is enrolled on a later pass. These bypass cases are eventually reconciled, not an ordered history of transient privacy changes.

The complete eligible-ID set matched **25/25** pending Directory contexts with blocked work; three private fixtures were excluded. ## Historical evidence: initial census

Social's internal `FIND_DIRECTORY_COMMUNITY_CENSUS` message returns bounded, UUID-keyset pages of public `local-hub` city/town communities. It selects only ID, name, slug, administrative area and locality type; a missing slug does not exclude a row. The server caps pages at 200 and validates cursors and limits. The endpoint is not connected to directory reconciliation or exposed as a public route.

## Incremental Social outbox (2026-11-04)

Social CommunityService create/update/delete and `seed-local-communities.ts` save a minimal identity/change or deletion tombstone in `community_directory_change` in the same transaction as the Community write. Create also saves the owner membership in that transaction. The table has no foreign key to Community, so a tombstone survives deletion. This is a notification log, not a complete eligibility history: it stores no snapshot of privacy or scope, and direct external SQL can bypass it. In particular it does not prove private → public transitions. Other Social writes and import paths still require audit; do not treat this as complete capture. Sequence allocation is not commit ordered; a simple highest-revision cursor can skip a transaction that commits late. A consumer needs a proven safe protocol, not just `revision > cursor`.

The Social Nx migration generator initially exposed unrelated election schema drift; that generated file was discarded. After aligning only the disposable generator database with the existing entity metadata, the generator produced `1793820819556-CommunityDirectoryChange.ts`, whose reviewed SQL creates only the outbox table. All Social migrations including this migration ran successfully on a separate fresh disposable PostGIS database. Social build, entity registration parity, outbox unit tests, a real PostgreSQL transaction rollback/commit test, and migration timestamp validation passed. No shared database, provider, source POC, or external publication was used. The public geometry gate remains pending.

This does not implement a consumer, durable directory cursor or contexts, revision fencing, provider-blocked work, queue scheduling, census repair, or automatic onboarding. Duplicate/out-of-order delivery, competing consumers, restart recovery, eligible/ineligible transitions, seed execution, full coverage, and SLO evidence remain untested. The PostgreSQL test covers outbox insertion failure and rollback, not every service path or a live end-to-end transition.

## Directory reconciliation primitive (2026-11-04)

This is **partial and not connected to the running worker or Social transport**. `DirectoryReconciler` serializes an authoritative read and directory write per community with a PostgreSQL transaction advisory lock. It stores a receipt for every distinct Social event identity in the same transaction as the town change; it never advances a sequence high-water mark. Every newly observed event clears geometry readiness, including a late lower-numbered event, and eligible towns get durable `blocked` provider-work records. Missing/ineligible towns are withdrawn and their work removed. Duplicate receipts are no-ops. The reader must return a complete current Social snapshot, including privacy and scope; no existing Social message supplies that contract here. This primitive does not prove ordered revisions, a consistent snapshot, or complete event delivery. In particular an unobserved private → public transition cannot be detected by an eligibility read; the public HTTP geometry gate stays pending.

The owning Nx generator produced `1793821061231-DirectoryFoundation.ts`; its SQL creates only the receipt and blocked-work tables, with matching drops. All directory migrations ran against a fresh disposable PostGIS 17 database. A focused PostGIS test passed for concurrent duplicate delivery, new town with null slug, late lower-numbered event, withdrawal and re-eligibility with geometry pending, and a new reconciler instance. Directory build, TypeScript check, and migration timestamp validation passed. The test uses a stub authoritative reader; it does not exercise Social, Redis, process failure during acknowledgement, or a network boundary. The disposable database container was removed after testing.

Still required: Social outbox claim/ack or equivalent with leases and replay (never a sequence cursor), integration with an authoritative current-policy transport and all writers, durable paginated census checkpoints and missing-town verification, concurrency and missed-event repair, bounded scheduling of blocked provider work, Redis and PostGIS recovery/end-to-end tests, and a privacy transition proof. Receipts have no retention policy; a safe one depends on the eventual acknowledgement protocol. No provider request, import, paid action, or publication was performed. The primitive is deliberately not scheduled until these contracts exist.

## Scheduled delivery and census increment (2026-11-04)

## S3 P1 acknowledgement repair (2026-11-04)

The destructive Social TCP acknowledgement handler and contract have been removed. Social retains every change, regardless of caller identity or directory receipt. The worker scans bounded pages using an in-memory position, applies each event through the directory transaction and its per-event receipt, and only advances after the entire page succeeds. An empty page restarts the next scan at the beginning; process restart also starts over. The scan position is not a durable high-water mark: a lower identity committed late is discovered on a subsequent scan. A lost result after commit replays the same event and its receipt makes the apply idempotent. Concurrent applies serialize per community. No credential or shared secret is used as evidence of application.

Evidence: the Social controller metadata test passes and confirms that neither a forged nor unauthenticated request can match the removed ACK command; this is not a live TCP penetration test. Focused worker tests pass for failed apply/lost response and late lower identities. On a newly created disposable PostGIS database, all directory migrations ran and three PostgreSQL tests passed, including replay after committed receipt/lost response, a lower late identity, concurrent receipt application, and withdrawal of a now-private town and its provider work. The database container was removed. The worker Nx test target did not pass as a whole because its separate Redis ACL suite requires disposable Redis credentials. The Social Nx test invocation also ran its full suite: the boundary test passed but the existing account-export disposition contract fails because the pre-existing new CommunityDirectoryChange entity is absent from its inventory and changes the expected metadata count. No provider calls or publication were performed.

**At this historical stage S3 was incomplete and not accepted.** Retention is intentionally unbounded; safe compaction, storage limits, throughput and maximum withdrawal latency require a separately proven protocol. Repeated full scans can be slow and under sustained arrivals may take arbitrarily long to complete, delaying discovery of late lower IDs. The existing Social TCP snapshot and census are not authenticated by this change and can reveal policy metadata to callers with network access; network isolation and service authentication remain unresolved. No live Social-to-directory TCP test, real Social transaction race, restart under load, or end-to-end public privacy proof was run. Receipts protect event application, not the security of the authoritative read. The public geometry endpoint must remain fail-closed until the outstanding S3 privacy and freshness gates are met.

Both affected Nx builds (`social` and `directory-worker`) passed after the earlier repair. `git diff --check` passed for tracked changes.

## S3 retention and service-boundary repair (2026-11-04)

The earlier statements about unauthenticated reads and unlimited outbox growth are superseded. Directory RPCs require `DIRECTORY_SOCIAL_SECRET` on both Social and worker; absent or mismatched credentials fail closed. The opt-in Compose overlay requires the same externally supplied value for both services. Do not commit the value; use a randomly generated, privately provisioned credential. This is a shared bearer credential over the existing TCP transport, not encryption or per-client identity: restrict the network, protect transport and configuration, rotate both ends together, and do not treat compromise of one service as contained. No authentication is claimed for unrelated Social RPCs. The census returns IDs only, unread notifications return revision and community ID, and the snapshot returns details only for currently eligible public local-hub cities/towns; other IDs return null. This also means null covers both absent and ineligible records.

Outbox producers serialize through a transaction-scoped advisory lock and reject the community transaction when 10,000 retained rows already exist. The limit bounds the repeatedly scanned outbox for writers that use this path, without deleting notifications or assuming sequence allocation implies commit order. It is intentionally disruptive: without an independently proven safe compaction or delivery protocol, the outbox eventually fills and community writes using this path stop; operators must monitor capacity and resolve the retention design before exhaustion, not delete rows on an unproven age or cursor rule. Existing rows above the cap, direct SQL or uninstrumented writers, manual deletion, old binaries, and separate consumers are outside that bound. Receipts have no independently enforced retention bound. The cap is not a freshness, throughput, or delivery guarantee. No schema migration was introduced.

Social's account-export disposition now explicitly excludes the operational outbox, whose community references may involve private records and have no account ownership selector. The in-memory metadata/disposition and unit authentication tests exercise their contracts, but do not prove authenticated transport, concurrent producer enforcement, exhaustive writer capture, or production deployment. S3 remains incomplete and publication remains gated.

Verification for this repair: Social Nx tests passed 45 suites / 573 tests, with 6 suites / 10 tests skipped (including the separately provisioned Social PostgreSQL disposition fixture). The full directory-worker Nx target passed 18/18 with no skips, using a disposable credentialed Redis, a migrated disposable PostGIS database, and the opt-in ACL, recovery and worker-restart cases. The disposable containers and test-created resources were removed. The restart test now waits for the final PostgreSQL TCP listener instead of the temporary initialization socket. Social and directory-worker Nx builds passed after the final code changes. No live authenticated Social RPC, concurrent Social cap test, production credential rotation, or end-to-end privacy/publication test was performed. Corepack's wrapper failed on this Node 22 environment; commands invoked its installed pnpm entry point directly. No provider, paid, or publication action was performed.

## Retention and scan follow-up (2026-11-04)

**At this historical stage S3 remained release-blocked and not accepted.** Delivery now alternates a forward traversal with a revisit traversal whose page limit grows after each forced wrap. This permits revisiting late commits even if the forward scan continually encounters new rows, while allowing the forward scan to reach the tail. It relies on eventual availability and successful page processing; this is not a bounded delivery-latency guarantee. A failed page leaves its position unchanged. The outbox limit may be set with `DIRECTORY_OUTBOX_MAX_EVENTS` (default 10000; invalid values fail closed); changing this limit does not fix retained-event exhaustion.

No Social cleanup endpoint is installed. The existing directory receipt is committed in a separate database and the Social RPC secret alone does not prove that a particular receipt committed. A cleanup design must bind each deletion to a trusted, authenticated delivery/receipt boundary, handle lost acknowledgements and concurrent workers, and bound receipt storage without allowing replay or database restore to erase newer work. The shared TCP network and credential provisioning must be qualified for that trust boundary. Until then every event remains in Social and community writes eventually fail at the configured cap; do not deploy this as an operational fix.

The opt-in Compose overlay still requires an externally provisioned isolated network, dedicated database and Redis credentials, and explicit migration. It is not integrated into normal local bootstrap. A deployment design must preserve the existing default network and provision isolated service connectivity, credentials, database, Redis ACL and migration ordering without per-town setup or user-supplied secrets. Periodic census starts a new pass but a live keyset page can miss inserts behind its cursor until a later pass; capture coverage and eventual repair require real database proof. Privacy withdrawal remains fail-closed at the geometry endpoint, not a proven end-to-end delivery SLO.

Focused worker unit tests cover failed apply retry, continuous nonempty forward pages, late low IDs, and a growing revisit window; they do not establish cross-database crash safety. Required evidence remains: throughput beyond a small cap with drained backlog and recovered writes, late and long-running transactions, concurrent writers/workers, crash before/after apply and cleanup, rejected unauthorized cleanup, receipt/cleanup races, census inserts behind cursor, and a real local-stack deployment. No new migration, provider calls, source POC, paid operation, or publication was performed in this follow-up.

## Runtime activation review (2026-11-05)

**At this historical stage S3 was blocked; runtime activation and v2 ACK were not implemented.** The existing unconditional startup and Social ACK guards remain in place. The activation coordinator can activate Social before it commits Directory's `enabled` checkpoint, so a Social-only active-pair check cannot authorize destructive ACKs during a partial activation.

The runtime authority path needs an authenticated Social active-pair read and an enabled-only Directory checkpoint check, with both epochs checked at every operation boundary. `readRecoveryEpochs` currently accepts only `blocked` checkpoints. Census checkpoint writes are outside an authority-locked transaction, census reconciliation does not acquire the event authority lock, and Social's normal read lock verifies the source epoch but not the bound recovery epoch. The worker needs a private authenticated Directory authority endpoint and must not receive database or signing secrets. Readiness and public status reads also need current authority checks; public geometry remains pending.

The v2 ACK primitive locks and verifies the Social pair and exact receipt identity, but the RPC is still fenced. Wiring it directly would not establish that Directory is enabled, particularly between the coordinator's two activation commits. A complete implementation must establish this condition without trusting epochs supplied by the caller and must preserve the operator's external fence for independent restores.

This review made no runtime changes and ran no migrated PostGIS, TCP, Redis, restart, or activation integration tests. No provider data, calls, publication, or paid operations were used.
