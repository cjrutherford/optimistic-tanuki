# S3 cleanup boundary

The worker sends each Social event identity to Directory's authenticated internal receipt endpoint. Directory reads the current Social snapshot under its per-community transaction lock, applies it and inserts the event receipt in the same transaction. Only after commit and a fresh matching receipt read does Directory return an HMAC-SHA256 attestation over `directory-receipt-v1:<revision>:<lowercase-community-uuid>`. Social checks the attestation and its separate worker credential before deleting that exact event. A lost response is safe to retry; an existing receipt with a different community is rejected. Directory's public geometry gate remains pending.

Provision three distinct secrets of at least 32 bytes: `DIRECTORY_SOCIAL_SECRET` to Social, Directory and worker; `DIRECTORY_SERVICE_SECRET` to Directory and worker; and `DIRECTORY_RECEIPT_SIGNING_SECRET` only to Directory and Social. Restrict the receipt port to trusted services on an isolated network; the bearer credential does not encrypt traffic, so use encrypted transport on any untrusted network. Do not expose it through the gateway. Rotate the signing secret on both services together; in-flight attestations signed with an old key fail closed and can be retried. The worker must have no Directory database credentials or database role memberships.

Use a separate migration owner and a non-owner Directory runtime role. Grant the runtime `CONNECT` to the database, `USAGE` on its schema, `SELECT, INSERT` on `directory_reconciliation_receipt`, and only the `SELECT, INSERT, UPDATE, DELETE` table privileges needed for the other Directory state tables. Do not grant runtime `UPDATE`, `DELETE`, `TRUNCATE`, ownership, or schema creation on receipts, directly or through inherited roles. Explicitly revoke public access and audit inherited privileges and ownership. A health-only role, if separately needed, must have only the read permissions needed for probes. These are operator provisioning requirements; Compose does not create or enforce roles.

Back up receipts consistently with Directory state, retaining them at least as long as Social events may be retried; restore both together. Restoring Directory to a point before Social deleted acknowledged events can lose reconciled state. Coordinate recovery with Social or run a complete authoritative reconciliation before relying on the projection; a current census cannot reconstruct every historical privacy transition. Database owners and administrators can alter or remove receipts, and backups can roll them back. Receipt storage is unbounded; do not compact it without a separately proven replay and restore protocol.
