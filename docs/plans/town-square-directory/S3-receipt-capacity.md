# S3 receipt capacity: bounded admission, restore gate open

Directory requires `DIRECTORY_RECEIPT_CAPACITY` (1–1,000,000) at startup. On an empty pool it provisions exactly that many slots under a database transaction lock; subsequent instances must use the same value. The generated migration creates a unique, non-null receipt slot with a foreign key to the pool. Admission holds the pool lock and inserts the receipt in the same transaction as projection updates. At capacity, the transaction fails and the worker must retry; the Social event remains pending. A duplicate receipt is still attestable. Cleanup takes the event lock and releases the slot only after Social confirms exact absence. Social errors retain it. This is backpressure, including for privacy changes; it is not a freshness guarantee. Monitor capacity and delivery failures.

The undeployed migration `1793838792651` was replaced with two Nx-generated schema migrations surrounding a TypeORM CLI-created data backfill, which entity metadata cannot infer. The default migration transaction holds the schema lock through allocation and constraint installation. The backfill takes an explicit exclusive receipt-table lock, preserves all existing identities and timestamps, and allocates distinct slots. Its rollback clears assignments and slots without deleting receipts; roll back the final constraint migration first. Do not use per-migration or nontransactional execution.

For an upgrade, stop all old Directory writers and workers before migration and keep them stopped until it commits. Supply `DIRECTORY_RECEIPT_CAPACITY` to the migration process itself, matching the subsequent application configuration and at least the retained receipt count. The shared Compose configuration forwards this variable to both the migration job and the application. Missing, invalid, or undersized capacity aborts the entire migration; do not delete receipts to proceed. Fresh databases also require valid migration capacity; the application initializes the empty pool on startup. Capacity changes still require an offline, reviewed procedure. Restrict direct pool and receipt writes to the Directory service and controlled migrations.

**Restore prohibition:** do not independently restore, roll back, clone into service, or reuse event identities in either Social or Directory. The current protocol has no independently protected, shared restore epoch or fence; a restore can revive a Social event or remove a Directory receipt and invalidate the exact-membership assumptions. A tested coordinated recovery protocol with independent epoch protection is a release gate. Backups and migrations here do not establish that protocol. No TTL or high-water deletion is safe.

The receipt server rechecks the committed receipt before signing and returns a retryable 503 if cleanup wins before that check. Cleanup can still occur after the check; no independent epoch fence makes a stale attestation safe across restore, so the prohibition remains necessary. This slice is not S3 release acceptance.
