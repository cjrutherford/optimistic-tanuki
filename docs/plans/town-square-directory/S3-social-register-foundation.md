# S3 Social register foundation — 2026-11-05

This is a partial capture increment, not S3 acceptance. Social now upserts one register row per community and a fresh token on each community change recorded by the existing transactional write paths, including inactive mode when no Social authority row exists. Deletions leave a tombstone without a community foreign key. Register updates and community mutations roll back together when called through those paths. Existing active-mode authority checks, legacy event handling, startup fences and ACK fences remain unchanged. The register does not contain snapshots and no consumer or cleanup interface exists.

The owning Nx generator created migration `1793903477715-CommunityDirectoryRegister.ts` against a fully migrated disposable database. The generated diff also included unrelated preexisting election schema drift and a nonce default alteration; those unrelated statements were removed after review, leaving only creation and reversal of the register table. The Social migration target applied the resulting migration to both the generation database and a second empty disposable PostGIS 17 database; migration validation passed. The register is excluded from account exports as internal state and registered in the runtime, migration and repository inventories.

Evidence: focused Social PostgreSQL tests passed 3/3 for coalescing, token change, tombstone retention, rollback, an actual inactive-mode community write and deletion with a legacy row preserved, and concurrent register upserts. Social outbox unit tests passed 10/10, entity parity unit tests 2/2, export-disposition tests 8/8, and the Social development build passed. An initial disposition test failed because the new entry lacked the required legacy-uncertainty wording; the corrected focused test passed. No provider, public data, or deployment activity occurred.

An independent review warned that register upsert alone cannot prove community operation order. The existing create, update, delete and seed helper paths acquire the global transaction-scoped source-epoch advisory lock before mutating the community, but arbitrary direct writers and the exported register helper do not acquire that lock. The concurrent test proves row upsert serialization only, not every actual mutation/delete interleaving. Do not use this helper as independent proof of capture ordering.

Outstanding: initialization/backfill of preexisting communities and retained legacy deletion identities, full writer coverage including direct SQL and imports, a complete real-service concurrency test, capture when authority exists or active mode is configured, restart and outage capacity evidence, authenticated current-state reads, receipt/cleanup design, independent-store recovery and two-store/Redis tests. In particular, the old source-authority gate and event cap still prevent the requested outage-independent active operation. Existing events were not converted or deleted. The table has no safe retirement policy and grows with distinct IDs, including tombstones. Public readiness and geometry remain fenced. See the durable onboarding plan for the next slices.
