# S3 restore fencing: blocked

The v1 receipt signature covers only revision and community ID. A Social restore can reuse that identity after Directory has garbage-collected the old receipt. Neither an independent Social restore nor an independent Directory restore can be detected reliably from restored state alone. A coordinated external recovery authority or operator procedure is required; historical no-loss cannot be inferred from independent backups.

As an interim fail-closed measure, Directory and its worker refuse to start, and Social's acknowledgement endpoint rejects all acknowledgements including valid v1 signatures. This affects ordinary restarts and delivery too. It does not stop already-running processes or protect alternate entrypoints or direct database access. Operators must fence all serving and workers externally before any restore, import, or failover. Do not resume these services with the v1 protocol. This is not a completed recovery procedure and this startup guard is not an epoch check.

Before restoring service, implement and verify durable source and Directory recovery epochs in their respective authoritative stores, immutable event nonces, v2 signed attestations binding both epochs and the complete event identity, and strict rejection of old or mixed versions at authenticated membership and ACK boundaries. A recovery workflow must externally fence serving and delivery before restore, rotate the relevant epochs using authority outside any restored snapshot, reconcile every currently eligible Social community and every Directory ID (including private and deleted withdrawals), persist and validate completion for those exact epochs, and only then explicitly enable serving and delivery. It must handle concurrent changes, retries and crashes without losing coverage. The precise backup coordination and authority remain design work; no independent-restore detection is claimed.

Required evidence remains: isolated real-database tests for old requests and attestations, epoch mismatch, withdrawals before enable, replay, and crash/restart; migration generation and fresh-database validation; and operational recovery drills. No provider, publication, deployment or production restore was performed.

## Social source epoch authority sub-slice (2026-11-04)

Social now has a separate singleton `community_directory_epoch` authority with a UUID, fenced flag, and initialization/update timestamps. In active mode, absence is fail-closed. Active Community changes lock that row in their mutation transaction and write its active epoch and a fresh nonce; fencing and rotation lock the same row. Initialization requires an empty authority and no null-epoch legacy outbox rows; rotation requires a previously fenced authority and the same legacy check. In active mode these checks halt Community mutations until an operator acts. The table is local to Social and does not detect a database restore or replace an external recovery authority. Source epochs on existing event rows are still mutable through direct SQL; do not grant untrusted database writers access.

The internal operator harness is `apps/social/src/source-epoch-operator.ts`. With the Social database connection configured, from `apps/social` run `TS_NODE_PROJECT=tsconfig.app.json node -r ts-node/register -r tsconfig-paths/register src/source-epoch-operator.ts <initialize|fence|rotate> --confirm-external-fence`. This is an explicit operator action, not an API. Before any operation externally stop/fence all old Social writers, Directory instances, and workers, and verify the target database independently; the confirmation flag does not itself establish that fence. `initialize` activates a newly generated epoch only when there is no authority and no legacy event. `fence` prevents subsequent compliant writers, and `rotate` creates and activates a different epoch after fencing. Do not interpret activation as permission to resume Directory, ACK, or public serving. Coordinates, credentials and epoch values are not printed by the harness.

Migration preserves existing events with null epochs. They remain blocked from safe delivery and block initialization or rotation until an explicit, reviewed, fenced backfill/reconciliation procedure exists; this slice does not implement that procedure. Never delete or assign epochs to legacy events merely to pass the check. Old application versions and direct SQL do not honor this authority, so external fencing is mandatory around upgrades, restores, and operator transitions. The source epoch is not externally protected against restore. Directory authority, v2 signatures and ACK, complete reconciliation, safe legacy backfill, and recovery drills remain outstanding; S3 remains blocked.

### Social feature mode and legacy events

`SOCIAL_DIRECTORY_MODE` is `inactive` by default; only `inactive` and `active` are accepted. Inactive Community changes, including deletes and seed writes, do not create outbox events or consume its capacity. Their transition history is **not preserved**. Pre-existing events, including null-epoch legacy events and their potentially private identifiers, remain untouched and must be protected. Active writes still require an unfenced source epoch, reject legacy rows, and enforce the outbox bound.

Directory and its worker must remain stopped: their unconditional restore-protocol startup guard refuses activation and public readiness, regardless of epoch initialization or mode configuration. Social also refuses Directory readiness and its guarded Directory endpoints until recovery exists. Before a future implementation removes that guard, it must provide and verify a fully fenced authoritative reconciliation over the union of all Social Community IDs and all Directory IDs, including deleted and private communities. It must invalidate every existing projection and all geometry, rebuild only from current authoritative eligibility, resolve legacy events through a separately authorized procedure without silently deleting them, and fence all old writers and consumers across the transition. The existing epoch operator and a snapshot of Social IDs alone cannot establish these guarantees. No implemented procedure currently authorizes Directory activation or claims that inactive transitions can be reconstructed.

### Epoch-bound Social reads (recovery building block)

Authenticated internal census, snapshot and membership requests carry `expectedSourceEpoch`. Each read locks and checks the authoritative Social epoch row inside its query transaction; a missing, fenced or different epoch fails closed, and fencing/rotation waits for an in-flight read. Membership also rejects a revision belonging to another epoch or community. Public eligibility retains its separate credential and minimal response. Existing readiness and ACK fences remain in place; these reads do not make startup or recovery safe.

The UUID-keyset census is a sequence of live pages, not a consistent snapshot: a concurrent insert behind a cursor can be missed, and updates/deletes can cross pages. Recovery must cover every mutation from a fenced baseline through completion using an explicitly proven, durable change stream or repeated fenced reconciliation. A bare maximum outbox revision or page boundary is insufficient: sequence allocation is not commit order, inactive writes have no outbox record, and acknowledgements can remove rows. Before enabling recovery, define an atomic capture boundary, account for in-flight transactions and inactive intervals, retain changes until reconciliation has durably covered them, and prove coverage across both stores. No such protocol is enabled by this sub-slice.
