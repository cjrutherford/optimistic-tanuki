## Proposed ADR: boundaries and accountability

**Approved by user on 2026-11-04:** Social `Community` remains the locality identity and privacy authority; a directory service owns separate directory persistence and evidence, with a worker for acquisition and processing. Gateway mediates public and operator access using existing authentication and permissions; provider identity never confers business-page ownership. The target projects are `apps/directory` and `apps/directory-worker`, with a separate Directory database; local infrastructure is accepted. Production topology, credentials and recovery remain S9 work. Social events/read contracts and reconciliation must cover existing and newly created or changed communities, with idempotency, retries and deletion/privacy withdrawal; database state, not seed JSON, drives onboarding.

At the user's direction, propose roles without named people: platform owner for service and operations; Social owner for eligibility/privacy; source-use reviewer for provider terms and field lineage; privacy/quality reviewer for sensitive locations and quality thresholds; authorized operator for runs, review and correction; security owner for gateway permissions. The user approved the [role responsibilities](S0-review-roles-proposal.md) on 2026-11-07 and agreed that one person may hold multiple roles. Actual individual and backup assignments remain open. Separate rights approval from deployment enablement. No operator action creates upstream rights. Owner-managed pages remain distinct: link only after verified authority and explicit matching/review; provider identity alone confers no ownership or subscription entitlement.

Proposed eligibility for review: every public, Local Hub-scoped city or town Community is represented by its stable UUID, including records with missing or conflicting slug or geography. The directory must expose an honest provisioning or exception status rather than silently excluding them. Safe public routing and acquisition require a resolvable identity and sufficient verified geography; private/restricted status and unknown app scope must not create public exposure. Validate actual enum, scope and privacy semantics before adopting this predicate. `localitySlug` is not a prerequisite. Coordinates alone are not a boundary: prefer reviewed boundary geometry and provenance, with a documented approximate fallback and overlap policy; never silently infer sensitive locations. Changes to privacy or rights must withdraw indexed, cached, direct-ID, map and export access.

**Approved by user on 2026-11-04:** keep a public town's directory visible with pending status when geography is missing or ambiguous, attempt automatic resolution, and hold ambiguous cases for review. Preserve each Community UUID for overlapping or duplicate towns; associate the same business with every matching town and flag ambiguous geometry. Exact boundary source and routing for missing slugs remain open.

**S1 authorization:** The user approved `apps/directory` and `apps/directory-worker` as project locations with isolated directory persistence and queues, and explicitly authorized using workspace Nx generator help and local plugin documentation in place of the unavailable `nx-generate` skill. S1 is limited to the foundation; later source-use and release gates remain in force.

Detailed evidence: [capability ledger](S0-capability-ledger.md), [source hash manifest](S0-source-manifest.md), [snapshot report](S0-snapshot-report.md), and [town census](S0-town-census.md). The manifest is a partial observation; the snapshot preserves the selected changed files, and the capability ledger identifies remaining coverage gaps. The census found one candidate outside both seed slug sets and one duplicate normalized city/admin-area/country group; both need explicit handling.
