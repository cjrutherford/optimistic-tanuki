# S2 private boundary review record

Goal: retain a candidate and its Social incarnation and change token in the separate Directory database for later authenticated review, without treating a candidate as verified or exposing it publicly.

- Store only the town UUID, Social source incarnation, change token, candidate source identity and review context. Limit size and reject malformed inputs; do not store a polygon, provider records or user credentials.
- Serialize record writes with the existing Directory town advisory lock and recovery authority. Candidate creation is private; a caller-supplied source assertion alone is not approval or evidence that Social is still current.
- Keep a candidate when reconciliation observes the same Social change token; delete it on a changed token, withdrawal or absence, and invalidate all candidates on authority recovery. A candidate may still be temporarily stale until a Social change is reconciled, so it must be checked again before a later decision. The record is never public serving authority and does not set geometry ready.
- Add focused tests for candidate persistence, invalid inputs, concurrent reconciliation, withdrawal and recovery invalidation on a disposable migrated PostGIS database. Generate schema migration with Directory's Nx target, inspect SQL, test fresh migration and validate migration naming.
- Subsequent work must add a separately authenticated reviewer decision and safe cross-service privacy/serving protocol. Do not claim S2 completion from this record.

## Implementation evidence — 2026-11-07

A private candidate table and `storeBoundaryCandidate` now retain one proposed GEOID, source fingerprint and Social incarnation/token per town. The helper validates the candidate shape, locks the existing recovery authority and town, checks a caller-provided current Social read and only stores for an eligible Directory town. Reconciliation retains the record only for the same change token and removes it on changed token or withdrawal; explicit town withdrawal and recovery remove it. This stores no polygon and does not set a boundary ready.

Directory's Nx migration generator produced `1794085555649-DirectoryFoundation.ts`; its SQL creates only the candidate table and its down drops it. The full chain applied to a fresh disposable PostGIS database with `DIRECTORY_RECEIPT_CAPACITY=1000`; migration validation passed. `directory:test-boundary-review` passed focused PostGIS checks for unchanged and changed tokens, mismatched source identities, invalid candidate, withdrawal during a write, explicit withdrawal and recovery. The existing town-geometry PostGIS test and Directory build passed. Intentional test-first failures appear in Nx task history.

The Social reader is a trusted callback assertion, not an authenticated operator. A source can change after that read, or by uncovered direct writes; reconciliation may lag. The record can therefore be temporarily stale and must never authorize publication. No production workflow calls this helper yet; no public or operator route was added. Candidate authenticity, authenticated reviewer decisions, cross-service lifecycle and public serving remain open.

## Private review read — 2026-11-07

The worker-side adapter accepts exactly one discovered candidate for the current Social incarnation and re-reads Social before storage, including comparing the actual locality fields and reference point. A generated follow-up migration adds a geography fingerprint; records created before fingerprints have an empty value and are rejected on read. `readCurrentBoundaryCandidate` checks the live Social token and geography against that fingerprint under the Directory authority/town locks. If Social is unavailable it throws without serving or erasing evidence; if the source differs, it removes and withholds the candidate.

The pending Directory runtime now exposes an internal candidate read protected by a separate `DIRECTORY_BOUNDARY_REVIEW_SECRET` (at least 32 bytes and distinct from its Social read secret); absent configuration disables the endpoint. The gateway route requires `AuthGuard` and the Owner Console scope guard, sends that credential internally and returns only the candidate review fields. The secret is passed through the checked-in Directory and gateway Compose configurations when supplied; it is not generated or set by this change. These are private read paths, not a decision or publication route.

The built Social, Directory and worker wire test with pinned Census archives passed candidate persistence, unchanged sweeps, internal credential rejection/acceptance and private-to-public withdrawal/restoration. ## Local candidate preparation

With a separately configured, running pending-only Directory/Social installation and independently obtained, hash-pinned Census Places and County Subdivision ZIP files for the town's state, an operator can invoke the Nx target `directory-worker:prepare-boundary-candidate`. It requires `DIRECTORY_COMMUNITY_ID`, `DIRECTORY_CENSUS_VINTAGE`, `DIRECTORY_CENSUS_PLACE_PATH`, `DIRECTORY_CENSUS_PLACE_SHA256`, `DIRECTORY_CENSUS_COUSUB_PATH` and `DIRECTORY_CENSUS_COUSUB_SHA256`, plus the existing Directory database URL, Social host/port and register-read secret, complete runtime identity and external-fence assertion. Supply secrets through the existing secure environment mechanism. The command uses only staged local ZIP files, disables DuckDB extension auto-installation and performs no provider request. It needs a locally installed DuckDB spatial extension.

A unique candidate is checked again against Social and stored privately; no candidate, ambiguity, an ineligible town or a changing source remains pending. The expected ZIP fingerprints are operator inputs, not proof of archive authenticity. The command neither approves a boundary nor starts a public route. The built-process wire test ran the actual command against synthetic Social records, separate disposable databases, authenticated TCP and pinned 2026 Georgia Census ZIP files, then checked the private candidate read, credential failures, source change and withdrawal/restoration.

The Owner Console page is linked from city actions in Community Operations, reuses shared card and button components, and distinguishes an unavailable service from no candidate. Focused page tests passed 3/3; Community Operations tests passed 14/14; the development build passed. A browser check at 1280 and 390 pixels used a simulated local session and synthetic candidate, confirmed the title, unverified status and no horizontal overflow. This is not evidence of a real authenticated browser session or public map behavior.

## 2026-11-08 continuation — private decision foundation

A reviewer decision now stores an immutable-by-application audit row with the authenticated gateway profile UUID, request UUID, decision, HTTPS `.gov` source URL, Social and Directory recovery identities, change token, Census identity/archive digest and geography fingerprint. The gateway requires its existing authenticated Owner Console role and forwards a separate `DIRECTORY_BOUNDARY_DECISION_SECRET`; Directory requires that secret to differ from its read credentials. The reviewer must explicitly attest to comparing the boundary and identifier; the UI leaves ambiguous cases pending. The request binds the exact fingerprint of the candidate loaded for review, checks the current candidate and Social geography under the Directory authority/town locks, and makes exact retries idempotent. Audit evidence survives candidate withdrawal; it is not serving or installation authority. The source domain constraint is conservative and does not establish that a particular government page substantiates a boundary. No specific boundary was approved and no real user review performed.

A fresh disposable PostGIS migration and the focused candidate/decision test passed, including stale fingerprint, stale Social geography, replay mismatch and withdrawal serialization. The gateway's focused suite passed 12/12, Directory runtime tests 7/7, Owner Console page tests 4/4, Directory typecheck, and Directory, gateway and Owner Console development builds passed. Compose configuration checks and migration-name validation passed. The generated migration's down operation was exercised on the disposable database and **drops review evidence**; a production rollback requires a separate evidence-preserving procedure. The Directory decision HTTP tests use synthetic dependencies; authenticated browser-to-Social-to-Directory operation and desktop/mobile visual checks remain unverified.

Still required: source-to-geometry installation that independently revalidates the approved archive and decision, current Social privacy checks on every serving path, reconciliation and recovery invalidation, labeled fallback and containment UI, authenticated live-stack evidence, and full S2 acceptance. Register reconciliation currently resets geometry to pending, and no decision is consumed as public authority. Source changes can occur after a Social read; retaining an audit row does not prove current eligibility or eliminate this race.

The next bounded implementation is specified in [the reviewed-geometry installation plan](S2-reviewed-geometry-installation-plan.md).

The 2026-11-08 continuation adds durable invalidation timestamps: observed privacy withdrawal, changed token or geography, candidate replacement and recovery invalidate applicable decisions while retaining their audit rows. An invalidated decision cannot be reused after restoration. The isolated PostGIS test covers that lifecycle and a candidate replacement during containment. A direct change that is never observed, or a change after the final cross-service check, remains outside the demonstrated guarantee.
