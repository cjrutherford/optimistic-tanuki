# S9 production-readiness plan

Status: planning, 2026-11-07. This is a work plan, not evidence that production is ready or permission to deploy, spend, import provider records or publish. The user accepted S1's local foundation and S3's isolated local pending-only milestone; their remaining production obligations are tracked here.

## Operating target

The user identified local `ot_social` as the intended Social source for this deployment, with separate Directory persistence. A distinct production hosting environment and its operating controls have not yet been established. The Directory API is to be a microservice reached through the gateway; the private operator surface belongs in the owner console. Normal onboarding should not require a per-town manual operation. Verified boundaries are preferred; any fallback must be clearly labeled. Source permissions and privacy policy remain separate decisions.

## Work and evidence

1. **Inventory and authority.** Identify the deployment environment, authoritative Social database and eligible-town census, and the owners of the Directory, Social privacy, operator, source-use and recovery functions. Compare exact eligible town IDs against Directory status without exposing private records. S0 remains open until its original acceptance is satisfied.
2. **Service composition and access.** Review the actual gateway, Directory, worker, PostgreSQL/PostGIS and Redis configuration and dependency readiness. Give services only required credentials, isolate queue namespaces and restrict metrics and operator routes. Demonstrate authorization using real endpoints, not only hidden UI controls. Identify a backup operator and a process for access revocation.
3. **Upgrade and recovery.** Test a representative existing installation as well as a fresh database. Capture backup and restore procedures, versions, schema transitions and a rollback approach that preserves privacy and rights decisions. The policy-membership migration's down path drops policy revocations: its successful schema revert is not proof of rights-preserving rollback. Demonstrate that an old process or restored store cannot overwrite newer privacy or withdrawal state, and document the external fence and coordinated restore sequence.
4. **Onboarding and repair.** Exercise existing and newly created eligible towns, missed events, duplicate delivery, restarts and privacy changes. Report the measured timing and population alongside the selected 15-minute pending-onboarding target; do not extrapolate isolated observations to production scale. Show truthful pending, blocked and failure statuses. The user approved daily reconciliation and 99% of eligible changes detected and queued within 24 hours; measure them, rather than infer compliance from a local test.
5. **Source, privacy and controls.** Do not enable acquisition or serving until the operation-specific source conditions and approvals exist. Implement authenticated owner-console correction/withdrawal; verify propagation to every actual public surface, including caches and exports when they exist. Keep residential and sensitive records blocked pending review and adult records opt-in. Preserve attribution and record an audit trail.
6. **Cost and monitoring.** Establish provider pricing, transfer costs, metering and a demonstrable stop mechanism, including retries and all towns. The user subsequently set a current $25/month budget. The ceiling is shared across all providers, all towns and retries, with every billed request counted; verify actual pricing, accounting and a hard stop. The prior instruction not to acquire real records yet remains in effect. Monitor backlog, blocked work, failures, freshness, withdrawal and spend; approved targets are refresh at least every 90 days, a stale flag after 120 days, and removal from public surfaces within 24 hours with an alert if missed. Apply stricter source conditions where required; specify ownership and response expectations.
7. **Release evidence.** Assemble a runbook, tested upgrade/restore transcript, access and rollback review, resource/cost report, privacy and withdrawal checks, plus outstanding exceptions. Record what is complete, deferred or unknown. Broad provider activation and public deployment need their own explicit source-use and rollout decisions.

## Immediate independent work

Map current deployment configuration and identify which checks already have local evidence; prepare representative upgrade and recovery test designs and operator-permission requirements without changing a shared stack or contacting providers. Record any missing authoritative environment or budget as an open decision, not as a reason to stop unrelated fixture-based work.
