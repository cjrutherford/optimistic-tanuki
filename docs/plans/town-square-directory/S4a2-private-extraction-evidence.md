# S4a.2 private extraction progress

**Status: implementation in progress; no real-source pilot or public use.** The POC source and its business records were not modified or copied. October object and row-group metadata only were inspected; the prior POC area is not authority for the current target boundaries.

The target checkout now contains a release preflight and conservative row-group metadata reader; a field-lineage rights evaluator with no bundled approval; a minimal private projection requiring explicit classification and ingest, retain and private-display rights; a private DuckDB extractor; and a PostgreSQL sink. The extractor binds its checkpoint identity to the supplied source, region, approval, projection and classifier identities and projects before handing results to the sink. The sink serializes competing writers and commits projected rows and the checkpoint together. A private withdrawal removes the scan's rows and persists a revocation under the same writer lock. Supplying digests is not proof of trusted authorization: independently provisioned approval and classification identities remain required.

Focused Nx tests cover preflight (seven cases), rights (five cases), projection (six cases), range proxy (six cases), and three synthetic DuckDB extraction scenarios. Each source requires an explicit per-field, per-operation grant; conflicting source mappings fail closed. DuckDB Node API 1.4.5-r.1 is now declared in the target workspace. On 2026-11-06, a disposable PostGIS database was migrated with the Directory Nx target and the private sink target passed three tests: competing writers, transaction rollback and a new sink instance; synthetic local and conditional-range Parquet through DuckDB, the rights projection and PostgreSQL with restart; and both orderings of withdrawal against an in-flight commit plus restart and preemptive revocation. This is local synthetic evidence, not production restore/failover evidence, source-policy approval, operational deployment, public serving or withdrawal from real indexes/caches.

The extractor supports a SHA-verified local Parquet file or a conditional-range remote mode using an ETag-pinned loopback proxy. It checks Parquet metadata but does not discard row groups or individual records based on bbox statistics: real DuckDB fixtures demonstrated that malformed or inconsistent bounds could otherwise be missed. It limits DuckDB threads, memory and temporary spill, and the remote policy must specify a per-run forwarded-byte budget. The budget stops the proxy forwarding a response that would exceed it, but upstream egress may occur before response headers are processed, so it is not a hard billing cap. The remote test used mocked HTTP responses and a synthetic file, not the October source. Its fixture does not establish actual-release transfer size or bandwidth, and the ETag is not a content SHA-256. It is not connected to the Directory runtime. No real provider records were acquired.

On 2026-11-07, focused regression tests first reproduced inherited permission elements and classification properties authorizing projections; the evaluator now requires dense own permission elements, and the projector requires own explicit classification values and a dense taxonomy hierarchy. Both focused Nx test targets and `directory:typecheck-overture` passed. A newly created disposable PostGIS 17 database was migrated using `directory:typeorm:migration:run` with `DIRECTORY_RECEIPT_CAPACITY=100`; the first attempt without that required setting failed and rolled back. `directory:test-overture-private-sink` passed 5/5 against it, including the synthetic DuckDB-to-projection-to-PostgreSQL path, restart and rollback, same- and different-scan concurrency, preemptive scan and row withdrawal, and stored-field filtering. `pnpm run validate:typeorm-migrations` passed. The three latest generated migrations were inspected: the checkpoint primary-key conversion's down migration requires an empty checkpoint table, and the other two create the scan lock and row-revocation tables. This is synthetic evidence only; an independent review of the changes and migration chain is outstanding.

At the time of this earlier evidence, cohort-wide policy withdrawal was unimplemented; the later continuation below records the synthetic database foundation. Trusted authorization and classifier provisioning, real-source approval, transfer/cost evidence, and the approved quality protocol remain open; this result does not establish pilot acceptance or public readiness.

On the subsequent 2026-11-07 continuation, a revoked row is skipped under the same scan lock as withdrawal while the rest of its batch and checkpoint commit atomically. Completion is persisted after extractor stream exhaustion, including empty scans and trailing unmatched records; the scan lock fences completion against competing commits and withdrawal. Completed retries return the recorded checkpoint without reading the source. Scan load and completion reads now serialize with withdrawal and detect stale checkpoints. The completion API relies on its caller to invoke it only at actual EOF. A new generated migration creates the marker table; it was inspected and applied alongside all Directory migrations on a fresh disposable PostGIS 17 database. The private sink PostgreSQL suite passed 8/8 on that database, including synthetic extraction, empty completion, completed retry, stale scanner, withdrawal and row skipping; extractor tests, sink unit tests, Directory typecheck, and migration validation passed. An independent read-only review found no concrete remaining race in these completion changes. These local tests do not prove production operation or policy-wide withdrawal. The proposed [cohort withdrawal boundary](S4a2-policy-withdrawal-design.md) remains unimplemented.

A subsequent implementation pass added durable policy membership and cohort withdrawal using the generated Directory migration `1794057360305`. The implementation worker reports a fresh disposable PostGIS migration and revert, 10 sink tests followed by two focused registration/withdrawal ordering tests, two sink unit tests, three extractor tests, typecheck and migration validation. These results have not been independently rerun after the final changes. A limited independent review noted that operator identity and authorization are not enforced by the sink, and that per-row revocation records remain after a whole-scan withdrawal; their retention policy remains to be decided. The reviewer did not examine all paths or independently verify the reported tests. **Downgrade caution:** the generated down migration drops policy and membership tables, including durable policy revocations; a successful schema revert is not evidence of safe rights-preserving rollback. Production use requires a recovery/rollback procedure that preserves and enforces revocations, plus trusted operator authorization and an independently authenticated policy authority. Membership is limited to 10,000 scans per policy; this does not bound retained row volume or withdrawal transaction duration. Real-source use, public serving and S4a.2 acceptance remain unapproved.

On the 2026-11-08 continuation, the complete current Directory migration chain was applied to a fresh disposable PostGIS 17 database and `directory:test-overture-private-sink` passed 11/11, including policy membership, cohort withdrawal, concurrent registration and rollback behavior. This is synthetic local database evidence only; the trusted operator/policy authority, retention, rights-preserving rollback, real-source use and approved quality protocol remain open.

The later 2026-11-08 continuation replaced one-transaction policy-cohort deletion with committed revocation followed by bounded resumable cleanup. The focused disposable PostGIS suite passed 12/12, including a 1,200-row interrupted cleanup, resume, denial after revocation, injected rollback after revocation and registration ordering. Physical rows can remain while cleanup is incomplete; the private sink denies the revoked policy throughout. Policy membership and revocation remain durable, and per-row revocation records are removed only after the policy is revoked and their scan is being purged. This is not evidence of public cache withdrawal, trusted operator authorization, provider data use, production scale, or safe downgrade.

The continuation added a mandatory per-attempt reservation callback to the private range proxy and an adapter to the shared local budget ledger. Matching fresh attempt IDs and current UTC periods are required before upstream requests; a replay cannot dispatch again. An already over-limit explicit range is rejected before reservation or upstream access. Synthetic proxy, extractor, sink and disposable-ledger tests cover the integration, including a failed upstream response retaining its reservation. The callback, maximum price, approval and classifier remain untrusted caller inputs until independently provisioned; open-ended/concurrent range egress and external billing remain unproven. No real provider records were acquired.
