## Readiness follow-up (2026-11-04)

The HTTP readiness response has a 2.5-second overall deadline, including PostgreSQL initialization and Redis operations. Failed or rejected probes return 503; unexpected handler errors also return 503. Concurrent requests share one underlying probe attempt. A timed-out attempt remains shared until every probe settles, preventing repeated stalled operations; if a driver never settles, readiness remains 503 and process restart or an operational recovery is required. The deadline does not cancel the underlying driver operation.

`NX_DAEMON=false NX_ISOLATE_PLUGINS=false pnpm exec nx run-many -t test build lint -p directory,directory-worker --parallel=2` passed (using the cached pnpm 11.0.9 launcher); Nx reported one cached task. Seven directory tests include real local HTTP requests exercising healthy, unavailable, rejected and stalled probes, PostGIS/table and Redis responses, recovery, routing, and repeated stalled requests. Dependency behaviors are simulated, not a network or deployment boundary test. An initial build exposed a Redis ping type mismatch; it was corrected and the final run passed. Nx labeled the earlier worker build failure flaky.

Queue evidence: the uncached `directory-worker:test` Nx target passed against a disposable local Redis container with persistence disabled. Two test-only ACL users were restricted to `s1test-a-*` and `s1test-b-*`; the test verified normal operations with each user and Redis returned `NOPERM` when the first user accessed the second prefix. Tests exercised duplicate identity, real consumption of `s1.check`, retry after failure, terminal failure, lease expiry and stale-claim rejection, and separate prefix identities. The test ACLs grant all commands and are not a production least-privilege policy. No deployment ACL, credentials, or production isolation has been verified. The uncached worker lint passed; the first build exposed a TypeScript type error, corrected before the worker build passed.

The earlier prototype retained completed and failed records indefinitely; the bounded replacement and its retention policy are described below. No administrative retry exists. Claims have 30-second leases, use worker clocks, and can be delivered more than once after expiry or a crash. Future processors must be idempotent and account for lease duration and clock synchronization; no exactly-once side effect is promised. Redis persistence, restart/recovery, concurrency under load, production ACLs and operational monitoring remain unverified. The worker exits on an unhandled queue operation error for external restart. The earlier prototype readiness probe executed EVAL, HGET, HGETALL and HSET against the actual queue key; a denied command, wrong key type or failed write returns not ready. The probe uses one reserved hash field. This proves only the current command/key access and write at probe time, not subsequent availability or durable storage. The test requires two supplied disposable Redis URLs and does not fall back to fixtures.

## Queue review follow-up (2026-11-04)

Queue records and their due times now live in one hash (`<prefix>:jobs-v2`). Enqueue, claim and finish each perform at most one Redis write after their reads; Lua serializes execution but provides no rollback, and a client timeout after a successful write still leaves the outcome uncertain. Retry enqueue with the same identity and inspect the retained record; expired claims can be redelivered. Processing is **at least once**, so processors must make their side effects idempotent. That prototype had unbounded hash iteration; it is superseded by the bounded jobs-v3 design below. This new key does not migrate jobs from the earlier two-key prototype; do not switch an installation with existing prototype jobs without an explicit drain or migration plan.

Uncached `directory-worker` Nx test, build and lint passed with a disposable Redis container (persistence disabled). Tests denied HSET via a restricted user after successful reads for enqueue, claim and completion, checked the original record after failure, restored permission and retried; they also exercised readiness denial/recovery and a wrong-type key. The test does not simulate Redis crashes, resource exhaustion, response loss, concurrent load, or persistence, and does not establish production network, ACL or deployment acceptance. The first test run exposed Redis's `ERR ACL failure in script` wording; the assertion was corrected and the final run passed. No provider call, import or publication was performed.

## Queue review round 2: bounded S1 queue (2026-11-04)

The new `<prefix>:jobs-v3` hash has an enforced default and hard maximum of 1,000 jobs (`DIRECTORY_QUEUE_MAX_JOBS`, 1–1,000). Each newly enqueued JSON record is limited to 5,000 UTF-8 bytes; transitions reject encoded records over 16,000 bytes. The two reserved metadata fields are additional. Each claim or readiness script checks HLEN before HGETALL, limiting a scan to at most 1,002 fields, assuming this key is written only by this queue. This is an execution and stored-record bound, not a latency guarantee or a bound on Redis allocator overhead. Redis 7 or newer is required for the readiness ACL check. Direct writes, malformed records, or oversized pre-existing values by other clients can violate the byte bound; isolate the prefix with ACLs. No FIFO or throughput guarantee is made.

The retention interval defaults to 86,400,000 ms and is configurable through `DIRECTORY_QUEUE_RETENTION_MS` from 1 ms to 2,592,000,000 ms (30 days). A poll removes at most one completed or failed record after that interval; waiting and active records are never evicted. Cleanup is opportunistic and may lag while workers are stopped or busy. A full queue rejects new identities with `Queue full`; producers must retry with backoff, and readiness indicates Redis access rather than spare capacity. Duplicate IDs return false while their record exists, including terminal records; after cleanup the ID can be reused and is a new job. Producers needing longer idempotency must maintain it independently. Existing jobs-v2 data is not migrated: drain or explicitly migrate before switching.

The first enqueue persists both settings in the same HSET as the job; all clients for the prefix must use identical settings or operations fail and readiness is false. Changing limits on a populated queue requires a planned drain/migration. Each enqueue, claim, finish, or cleanup makes at most one Redis mutation, including configuration initialization. A failed or timed-out operation remains outcome-uncertain; inspect by ID and account for at-least-once delivery. Lease and retention timing use worker clocks; clock skew and long processing can cause early expiry or redelivery. Readiness checks the queue key, bounded scan, write, and cleanup ACL, but not durability, future availability or capacity.

Round 3 queue ACL follow-up: all queue operations use the single `${prefix}:jobs-v3` key. Enqueue uses EVAL, HGET, HLEN, HEXISTS and HSET; claim uses EVAL, HGET, HLEN, HGETALL, HDEL and HSET; finish uses EVAL, HGET, HLEN and HSET; get uses HGET directly. Readiness invokes EVAL and explicitly checks each hash command against that key before configuration validation, the bounded scan and its reserved-field write. It catches permission, configuration and key-type failures and returns false. Its write is confined to `!readiness`; it does not alter job records. This remains an access check, not a guarantee of later operations.
