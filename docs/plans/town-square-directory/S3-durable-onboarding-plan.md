# S3 durable onboarding: proposed delivery slices

**Goal:** Automatically reconcile every eligible Social town into a private pending Directory projection without blocking ordinary Social writes during a Directory outage, while preserving a separately fenced recovery path.

**Status:** Design and proof plan only; no protocol below is enabled or accepted. The user selected durable onboarding on 2026-11-05. Public ready geometry, provider work, paid calls, and business-data publication remain gated.

## Candidate: source-owned coalescing state

Capture the current state of each affected community in the same Social transaction as its mutation, using a monotonically changing per-community version or unique change token. Keep at most one dirty record per community rather than retaining one row per mutation. Directory repeatedly reads dirty entries and reconciles the current Social state into its private pending projection. It can request conditional acknowledgement only for the exact version it read, after the projection transaction commits; a concurrent mutation changes the version and prevents that acknowledgement from clearing newer work. Failed requests or ambiguous responses are retried idempotently. The dirty record must preserve deletion/tombstone information until safely reconciled; its storage is proportional to distinct affected communities, including uncollected deletions, not bounded independently of their number. Database storage exhaustion remains a real failure and requires capacity monitoring and an operational response.

Do not interpret this as a complete protocol. The source database must authenticate and authorize the consumer and validate acknowledgement authority; a caller-supplied version or secret alone does not prove a remote commit. A lost Directory connection, an old or replayed acknowledgement, a restored store, concurrent workers, and late transactions must be accounted for before cleanup is enabled. In particular, conditional version matching prevents deletion of *newer versions*, but does not by itself prove that the corresponding Directory write is durable or belongs to the currently authorized incarnation. A receipt or a different verifiable boundary and a clearly defined external fence are still required. No claim of cross-database atomicity is made.

Repeated full census remains a repair mechanism, not an ordered event log or proof of every intermediate privacy change. A private → public → private sequence may be coalesced; no public serving or provider side effects may depend on the projection until their privacy authorization and revocation semantics are separately proven. Readiness must report capture/reconciliation health and must not equate a running process with complete coverage.

## Writer coverage prerequisite

`community.service.ts` routes create, general update, and delete through the current outbox helper, and the local seed uses it. However, membership operations and manager assignment also call `communityRepo.save(community)` on loaded entities. Those whole-entity saves are outside the capture helper. They can race with privacy or locality changes and potentially write stale fields back without a directory event; whether each call can do so must be established with a real database race test. Field-specific updates or correctly locked, directory-aware writes should prevent unrelated paths from restoring stale policy fields. Inspect every Social, seed/import, SQL, and privileged direct-writer path, and document which policy fields each can alter. Database privileges and operator procedures must cover writers outside the application.

## Reviewable implementation sequence

1. **Writer isolation:** reproduce the stale-entity race with a real migrated Social database; replace unsafe whole-entity saves with field-scoped writes where appropriate and test concurrent privacy changes. Inventory remaining writers. This is prerequisite work only; existing global authority, startup, and ACK fences remain unchanged.
2. **Social capture:** design and generate the owning Social TypeORM migration and implement transactional coalescing, deletion tombstones, and restart-safe reads. Prove repeated updates coalesce; concurrent writes, rollback, and late commits remain represented; out-of-service Directory does not cause an event-count cap to reject ordinary writes. Explicitly address initialization and preexisting legacy events without silently discarding them.
3. **Directory reconciliation and secure cleanup:** define authentication, exact-version acknowledgement and durable receipt/authority semantics, before exposing a destructive endpoint. Prove crash and retry before/after each commit, multiple workers, stale acknowledgements, and receipt capacity. If proof needs an always-on external authority, define its availability and operator ownership rather than substituting a database-local epoch.
4. **Recovery and complete coverage:** under an external fence, stop and drain every serving process, worker, and direct writer; restore or rebuild consistently; rotate or rebind authority; reconcile and validate complete eligible ID sets; then resume. Exercise independent restores, late or ambiguous operations, privacy withdrawal, restart, and the full disposable two-PostgreSQL-plus-Redis path. Keep public geometry pending until its own lifecycle proof is accepted.

## Verification boundaries

Each slice requires targeted tests and recorded human-reviewable evidence. Social and Directory migrations must be generated via owning Nx targets, reviewed, run against fresh disposable databases, and validated with `pnpm run validate:typeorm-migrations`. Runtime acceptance needs real services and credentials, not just unit tests or old images. Record skipped checks. No automatic onboarding or S3 acceptance is implied by this plan.

## Persistence behavior reproduction (2026-11-05)

A disposable PostgreSQL 16 container and a minimal TypeORM `EntitySchema` reproduced the relevant behavior: load a public row, update its privacy to private through a separate repository update, increment the stale entity's member count and save it. The resulting row was public with the incremented count. The container was stopped and removed. This confirms the TypeORM stale-save mechanism with the installed library; it does not yet exercise the real `Community` entity, an application method, the migrated Social schema, or an outbox. The application paths above require their own regression tests before a fix is claimed.

## Writer isolation increment (2026-11-05)

Manager appointment and revocation, membership count saves, ordinary community updates, and the existing-community local seed now persist only their intended fields instead of saving a previously loaded whole entity. The ordinary update and seed still use the existing transaction/outbox helper. This prevents those unrelated field updates from writing stale privacy values; it does not solve concurrent writes to the *same* field, guarantee atomic member counts, or prove every direct database writer is covered. Returned in-memory entities may still contain values read before a concurrent update.

A freshly created disposable PostGIS 17 Social database was migrated with the Social Nx migration target. On the actual `Community` entity and service methods, the focused regression reproduced stale privacy restoration for manager appointment, revocation, and an unrelated community update before the fix. After the changes, four focused PostgreSQL cases passed: appointment, revocation, membership removal, and unrelated update all preserved a concurrent private value. The membership test simulates the membership repository while using the real community repository. The Social service unit file passed 32 tests and the Social development build passed. The seed-specific race was not run, nor were all membership paths tested against PostgreSQL. No cross-service delivery, recovery, or public privacy lifecycle claim follows.

An initial misconfigured test filter ran additional Social suites; unrelated existing authority tests failed because their fixtures do not provide the newly required runtime authority. The service unit fixture was updated to represent an active transaction, and its focused file passed. Results from the broad accidental run are not a passing Social suite.

A separate planning review recommends a Social-owned register retaining one current row and fresh token per community, including tombstones, with atomic mutation/capture and exact-token conditional acknowledgement. That is a candidate only: authenticated committed receipts, credential and incarnation handling, legacy-event conversion, external fencing, storage growth, and recovery must be designed and tested before any cleanup or startup fence is lifted. A coalesced private projection cannot establish every intermediate privacy transition or authorize provider side effects.

Independent review noted the seed path and additional membership operations lack their own migrated race tests. The partial-save behavior was exercised by the ordinary-update database test, but this is not a direct seed proof. The test opt-in now rejects an incorrectly specified marker instead of silently skipping. These gaps remain open; the reviewer did not establish a failing seed interleaving.

## Candidate Social-only capture transition (design review)

A bounded register-only mode requires a durable baseline marker bound to the current source epoch, committed in the same transaction as initialization. An operator transition under the external all-writer fence can enter a distinct `capture-only` phase only from a fenced, unbound authority with a matching marker. Social writes then hold the existing pre-mutation authority lock and update the coalescing register without consuming legacy outbox capacity; old legacy rows are preserved. Recovery must first revoke capture and invalidate the marker under that same lock before traversal. Directory startup, readiness, recovery-only reads and ACKs cannot treat the capture-only phase as active authority.

Before any rollout, stop and drain old Social binaries, Directory processes and direct writers: old consumers cannot infer current coverage from a stalled legacy stream, and rolling back to an old binary requires a new fence and authoritative reconciliation. A restored database may restore a writable phase and marker along with its data, so those local fields cannot detect restore. The operator must fence, rotate authority, initialize and explicitly re-enter capture before resuming. Register storage still grows with distinct community IDs and tombstones. These are required protocol conditions, not evidence that production recovery is safe.

Acceptance for the bounded implementation requires a generated Social migration; baseline-marker atomicity and rotation checks; rejected wrong/missing phase and epoch; real community mutation, rollback and concurrency tests above the old outbox cap with Directory unavailable; preserved legacy rows; recovery revocation; and unchanged startup, readiness and ACK fences. Full writer coverage, direct-writer controls, authenticated delivery, cleanup and cross-store restore are later gates.
