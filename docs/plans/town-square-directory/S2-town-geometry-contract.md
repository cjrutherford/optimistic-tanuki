## Contract and review

Social Community UUID is the directory town primary key. Name, nullable slug, and nullable administrative area are mutable descriptions, not keys. Distinct UUIDs remain distinct even for identical names and boundaries. Eligibility is persisted independently of geometry; the caller must derive it from Social's public local-hub city/town policy. An internal Social snapshot adapter applies the public local-hub city/town predicate without requiring either slug. It is not connected to an authoritative Social transport or reconciler. No briefing locality slug is used by this contract. S3 must reconcile every qualifying Community, including missing slugs/geography, and handle changes in eligibility.

A new mapping has `pending` geometry and version 0. Withdrawal resets readiness; restoring eligibility requires a new boundary submission. Boundary submissions while ineligible are rejected, and prior versions are retained only for audit. A boundary submission requires source, vintage and rights metadata, a WGS84 GeoJSON Polygon or MultiPolygon, finite two-dimensional coordinates within longitude ±180 and latitude ±90, and a nonempty PostGIS-valid geometry. Invalid submissions set `invalid`; no version is added. A successful submission creates an immutable numbered version under a row lock and sets `ready`. The prior versions remain available for audit. An invalid update retains prior versions but does not serve them as ready. There is no selected authoritative source, no imported boundaries, no publication, and no assertion that supplied metadata grants rights. Missing boundaries remain pending; source selection, rights review, real map examples and resolution belong to later reviewed work.

Point validation uses WGS84 coordinates and PostGIS `ST_Covers`: exterior and hole boundaries count, hole interiors do not. A point on a shared border or in overlapping polygons may match multiple UUIDs; `ambiguous` flags this and all matching IDs are returned, allowing shared associations. Per-town validation explicitly returns pending, invalid or ineligible instead of reporting an empty successful result. Invalid coordinates are rejected. The global point lookup is explicitly labeled `geometry-candidates` with `complete: false`; it is not a directory response or a completeness claim. Antimeridian interpretation and authoritative boundary disputes require policy review before public use.

## Social and gateway integration follow-up (2026-11-04)

The user resolved the earlier transport and route decisions: town status and point validation are public through the gateway; service traffic is private; operator actions require authentication. Social now provides a UUID lookup over its existing TCP transport, selecting only ID and locality type and returning only ID for public Local Hub cities/towns. Private, missing, wrong-scope and other locality records return the same null response. Gateway returns only the caller-supplied UUID and pending status, with no Social descriptive metadata. Gateway exposes GET `/api/directory/towns/:id/status` and `/api/directory/towns/:id/validate?longitude=...&latitude=...`; it validates input, asks Social first, strips unexpected fields, and calls the directory's private read-only HTTP listener. Missing/ineligible is 404; Social, directory, malformed service response and timeouts fail as 503. The opt-in Compose override connects gateway to the supplied directory network and publishes no directory port. Network isolation and ingress policy remain operator responsibilities. No operator mutation route was introduced; any future operator route must authenticate and authorize before mutation.

**Safety limitation:** Every eligible response is `pending`, including for stored ready geometry. A point validation does not return `covers` yet. Request-time lookup cannot detect a private-to-public transition between reads, so neither old geometry nor a false empty result is exposed. S3 must implement durable ordered transition tracking/reconciliation and a safe release gate before enabling ready geometry. A privacy change racing a single in-flight lookup is not atomic across services: an already authorized request can still return the caller-supplied UUID and pending status after withdrawal. Subsequent checks return 404 after Social observes the withdrawal. Response codes and timing can reveal eligibility at the lookup time, and service availability; this public status API does not provide existence or timing secrecy. Neither response bodies nor response timing are conditioned on Social descriptive fields, which are not selected. Repeated eligibility reads cannot guarantee atomic revocation. The directory performs no public-request writes, onboarding, provider access or publication.

## Register-only pending status with an approximate point

The accepted S3 register-only runtime and the older gateway eligibility read used different Social authority modes. An optional, separately credentialed register-only path now lets the gateway call Directory's `/internal/register-towns/:id/status`; Directory checks its pinned recovery/sweep authority and reads current eligible geography from Social twice. A valid current Social reference point is returned with the label “Approximate town location; verified boundary unavailable.” Missing or invalid coordinates return no point, and boundary status remains `pending`. A private or absent Social community returns 404; unavailable authority or malformed responses fail closed. The legacy gateway path remains in place when the new credential is not configured.

The service-to-service credential is `DIRECTORY_PENDING_READ_SECRET`, supplied separately to the gateway and Directory. Directory rejects a value shorter than 32 bytes or equal to its Social read or private-review credential. The route remains unavailable until configured; this change does not configure or activate it on the shared stack. The point comes from Social, not cached Directory geography; no polygon, containment result or reviewed boundary is claimed. A request can still complete using an eligible Social read immediately before a concurrent privacy change, and direct write/change-and-revert or restore behavior beyond the tested cases remains a lifecycle limitation.

## Community list privacy boundary

While connecting the Owner Console review page, source inspection found that the public `GET /communities` gateway handler previously treated a caller-supplied `owner-console` scope header as authority to list all scopes, while its Social source returned private locality records too. The gateway now requires a guard-verified session profile and an Owner Console owner/admin role before using that cross-scope path. Ordinary scoped lists return only records explicitly marked public and matching the requested scope; a missing scope returns an empty list. An unavailable permissions service fails closed. The owner path continues to return private records to an authorized owner.

These are handler/guard-boundary tests, not a claim that every other Social or Directory public route has been audited.
