# S1 container build and isolated readiness evidence

Date: 2026-11-04. Scope: Docker build and disposable runtime check; no provider calls, imports, or shared stack changes.

## Build

A single reproduction used `timeout --signal=TERM --kill-after=15s 300s docker compose -f apps/directory/compose.yaml --profile migration --progress plain build`, with placeholder values for the required database, Redis, queue prefix and network variables. It exited **0**, producing `directory-directory`, `directory-directory-worker`, and `directory-directory-migrate`. Both Nx application builds reported success. Full captured output: `/tmp/s1-docker-build.RNQoUF.log` (local, ephemeral).

During dependency installation pnpm logged, for example, `[WARN] GET https://registry.npmjs.org/@excalidraw/excalidraw/-/excalidraw-0.18.1.tgz error (23). Will retry in 10 seconds. 2 retries left.` Similar warnings and one `UND_ERR_SOCKET` appeared; installation eventually completed. This reproduces the warning signature but does not establish the cause of error 23 or explain the earlier deadline failure. The successful build does not prove these warnings are resolved. Docker reported `overlay2` and `/var/lib/docker`; prior preflight reported substantial free disk space.

## Disposable runtime check

A 180-second bounded script created a uniquely named internal network and disposable PostGIS 17-3.5 and Redis Alpine containers with test-only credentials, no published ports and no persistent volumes. The migration image ran `directory:typeorm:migration:run` and Nx reported success; Nx Cloud also reported `EAI_AGAIN`, expected to be possible on an internal network. The directory image returned `HTTP 200 {"ready":true}` from its readiness endpoint.

The worker did **not** become ready. Its container exited with `Error: Cannot find module 'pg'`, `code: 'MODULE_NOT_FOUND'`, require stack `/app/main.js`. Its built image's `/app/package.json` lists only `redis`, `reflect-metadata` and `tslib` as dependencies. This supports a missing runtime dependency in generated worker packaging as the immediate hypothesis; the underlying build configuration has not been corrected or verified here. The cross-container readiness request was not reached. The check exited 1. Captured output: `/tmp/s1-isolated-check.log` (local, ephemeral).

The disposable containers and network were removed by the script's exit trap; subsequent Docker listings showed no `s1-check-` containers or networks. Built images and build cache remain; no destructive cleanup was performed. This does not verify Compose health checks, production credentials or isolation policy, or a successful worker runtime. Rebuild and rerun isolated readiness and network checks after the worker packaging issue is fixed.

## Packaging fix and isolated rerun

The worker imports the directory foundation through a TypeScript path alias. Its webpack bundle contains external `pg` and `typeorm` requires, but Nx's file-level dependency discovery did not include those packages in the worker's generated manifest. Adding an Nx implicit project dependency alone did not change that manifest. The worker Docker builder now seeds a project manifest with `pg` and `typeorm` versions read from the frozen-lockfile install before invoking Nx; Nx generates the production manifest and lockfile, and the final image installs from that lockfile. If the aliased foundation gains other external dependencies, this explicit declaration must be updated.

On 2026-11-04, `timeout --signal=TERM --kill-after=15s 600s docker compose -f apps/directory/compose.yaml --profile migration --progress plain build` exited 0, followed by the same bounded Compose build for `directory-worker` after the fix (exit 0). Docker's context excludes host `node_modules`; the worker production install included `pg 8.23.0`, `typeorm 0.3.31`, `redis 5.12.1`, `reflect-metadata 0.2.2`, and `tslib 2.8.1`. Captured logs: `/tmp/s1-packaging-build.log` and `/tmp/s1-packaging-worker-build.log` (local, ephemeral). The builds downloaded packages from the registry and emitted slow-download warnings; they do not establish that earlier transient registry errors are resolved.

A bounded 180-second run of `/tmp/s1-packaging-check.sh` (log `/tmp/s1-packaging-check.log`, both local and ephemeral) created two unique internal Docker networks and disposable PostGIS and Redis containers, with test-only credentials, no published ports, and no persistent volumes. The migration image successfully ran `directory:typeorm:migration:run` against the fresh database. The API and worker each returned `HTTP 200 {"ready":true}` locally, and the API container reached the worker readiness endpoint with the same result. Every non-builtin webpack external emitted in the worker bundle resolved inside its production image: `reflect-metadata`, `tslib`, `redis`, `pg`, and `typeorm`. A container on the second internal network could not reach the API container's IP (`ENETUNREACH`). The script exited 0 and its exit trap removed its containers and networks; subsequent Docker listings found no `s1-pkg-` containers or networks. Built images and cache remain.

This verifies the exercised startup, migration and readiness paths and one cross-network boundary, not all dynamic dependency paths, Compose healthcheck timing, host firewall or production isolation policy, production credentials, or queue processing. No provider calls, imports, or publication were performed. Concurrent source changes after the Docker build context was captured require a fresh build and relevant validation.
