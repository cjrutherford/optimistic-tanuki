# S3 Social register initialization — 2026-11-05

The operator-only `initialize-register --confirm-external-fence` operation creates missing dirty register entries for all current Social communities and all community UUIDs retained in the legacy outbox. A legacy ID absent from Social becomes a deletion tombstone; the event rows are untouched. Existing dirty register rows with operations matching current community existence retain their token and timestamp, so a retry is stable. Contradictory or clean existing rows cause the whole transaction to fail instead of silently overwriting them. This operation does not remove legacy events, authorize cleanup, enable active capture or start Directory.

The caller must first stop and drain all Social and Directory workers, serving processes and direct database writers, and maintain that external fence throughout reconciliation and activation. The confirmation flag is only an operator assertion and does not enforce the fence. The initializer also requires exactly one existing Social authority row in fenced phase; create that authority through the existing operator procedure if absent. It takes the existing Social epoch advisory transaction lock, locks the authority row, and obtains `SHARE ROW EXCLUSIVE` locks on community, legacy-event and register tables. A three-second lock timeout fails the operation if another writer is active. Those database locks protect only the initialization transaction, not the period after it commits. A separately reviewed operational procedure is still required for deployment.

A freshly migrated disposable PostGIS 17 Social database passed six focused PostgreSQL tests: current and absent legacy IDs, event preservation and retry, contradiction rejection, required external assertion, active versus fenced authority, missing authority, and a direct writer holding a conflicting table lock. The actual operator command also completed against that disposable database. Social development build passed. An intermediate new test failed because its fixture misread TypeORM's DELETE RETURNING result; the fixture was corrected and the final focused run passed. No schema migration was added and no live database was touched.

Independent review initially reported a missing legacy union; the actual query includes `community_directory_change` and its PostgreSQL test covers a legacy-only UUID. The review correctly identified missing authority as a gap; the implementation now rejects it. A second review task could not inspect the repository, so no independent final review is claimed.

Limits: no complete service-writer ordering proof, no production fence enforcement, no proof of authenticated delivery, restore, worker restart, outage operation in active mode, exact receipt cleanup or town coverage in Directory. A contradictory register requires a separately designed reconciliation procedure. Nothing here marks S3 complete or enables public geometry.

## Concurrent initialization and direct-writer checks

On a newly migrated disposable PostGIS 17 database, the focused initialization suite passed 8/8, adding two checks: concurrent initializer calls leave exactly one register entry and a subsequent retry preserves its token; and a direct SQL `UPDATE` attempting to acquire a community write lock is observed in `pg_blocking_pids` waiting specifically for the initializer's database session while its table locks are held. The SQL update targets no rows; this demonstrates lock exclusion during the transaction, not capture of arbitrary direct writes or enforcement after commit. The existing test also verifies initialization fails on lock timeout when a writer already holds a conflicting lock.
