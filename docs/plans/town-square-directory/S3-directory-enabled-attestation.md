# Directory enabled attestation

The operator must independently fence all Social writers, Directory instances and workers for the entire transition and retry. The confirmation flag is an assertion, not a fence. Run `directory-enable-operator --confirm-external-fence <sourceEpoch> <recoveryEpoch> <owner> <activationId> <socialGeneration> <directoryGeneration>`, with the Social prepared **attestation object** on stdin (the Social operator outputs it in its `attestation` property). Set `SOCIAL_DATABASE_URL`, `DIRECTORY_DATABASE_URL`, `SOCIAL_OPERATOR_PUBLIC_KEY_FILE`, `DIRECTORY_OPERATOR_PUBLIC_KEY_FILE`, `DIRECTORY_OPERATOR_PRIVATE_KEY_FILE`, `SOCIAL_OPERATOR_KEY_ID`, and `DIRECTORY_OPERATOR_KEY_ID` in the operator environment. Keep the Directory private key file restricted to the operator. The keys and key IDs must be distinct; protect stdout as an operator artifact.

The coordinator acquires both database connections before taking locks, then takes the Directory recovery transaction lock before the authoritative Social row lock. It checks the fenced prepared state, all six identity fields, persisted traversal digest and the Social signature while holding the Social lock. The Directory recovery lock remains held through the Directory transaction; receipt-pool locking follows both authority locks. Connection acquisition has a two-second deadline, and both transactions set a two-second lock timeout and ten-second statement timeout. A matching traversed checkpoint retires existing receipts under the pool lock, leaves slots and towns intact, and stores the signed-envelope digest and retirement count and digest before entering enabled. The retirement digest hashes JSON of an array containing `directory-retirement-v1` followed by event-ID-sorted arrays of event ID, community ID, slot ID, nonce, source epoch and recovery epoch. The signed-envelope digest is the shared contract's `operatorAttestationDigest` of the verified Social attestation. Only after the Directory commit does the operator sign the `directory-enabled` attestation with that digest as its `social-prepared-v1` prerequisite. Exact retry returns the stored retirement result and deterministic signed payload; it never deletes newer receipts. Legacy enabled rows without the stored payload fail closed.

These local phases do not certify the external fence or activate serving. Directory and worker startup and ACK remain disabled pending the final handoff. The two stores do not form a distributed transaction: if the process stops after Directory commits, retry with the same proof and fence; if Social changes before retry, the retry fails closed and requires operator investigation. Production key custody and operations are outside this slice.

Verification used two disposable PostGIS 17 databases with the full Social and Directory migration chains. The focused two-store test exercised the real Social prepare function, forged signatures, wrong key/purpose and all six identities, a changed authoritative digest, transaction rollback, concurrent enable calls, retry after a newer receipt, preserved town and slots, operator key rejection, explicit fence confirmation, and repeatable signed output. The Directory Nx build and non-database test target passed (24 passed, 20 skipped); TypeScript checking and the migration validator passed. A separate fresh Directory database ran the full migration chain, reverted the generated migration, and reapplied it. The test models a crash after commit by retrying the committed transition before signing; it does not forcibly kill a process at each commit boundary or prove external fencing, production runtime, final handoff, startup, or ACK.

**Lock-order review follow-up (2026-11-05):** On two freshly migrated disposable PostGIS databases, a deterministic barrier held a real Directory apply at its Social membership call while enable waited for the Directory recovery advisory lock. The actual Social membership method acquired its shared authority lock and rejected the prepared, fenced authority; apply rolled back, enable then rejected the blocked checkpoint, and the original receipt and checkpoint remained intact. A separate held recovery lock caused enable to reject within the configured lock deadline without changing the checkpoint or receipt. The existing focused test also exercised forced update rollback, concurrent enable, exact retry, and preservation of a later receipt: `TS_NODE_PROJECT=apps/directory/tsconfig.json S3_SOCIAL_TEST_URL=... S3_DIRECTORY_TEST_URL=... node -r ts-node/register/transpile-only --test apps/directory/test/directory-enabled.test.js` passed 2/2. Directory Nx build passed; Nx test passed 24 with 20 database cases skipped. The databases were separate databases on one local PostGIS server; this does not prove network-partition behavior, an external fence, or live deployment. The operator's external fence remains mandatory throughout transition and retry.
