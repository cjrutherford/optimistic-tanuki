# S3 pending-only operations — review draft

This procedure is for the pending register protocol. It does not authorize production deployment, public business data, provider acquisition, geometry publication, or legacy event acknowledgements. A recovery must be reviewed against the actual deployment's database, network, credential and backup controls before use.

## Prerequisites and fence

- Identify the authoritative Social and Directory stores, backup points, operators, and independent configuration store. Record the prior six-field Directory identity if one exists.
- Stop and drain **all** old Social and Directory processes, serving instances, workers, imports, seed jobs and direct database writers. Block their reconnection with deployment, network and database credential controls. Keep old binaries and direct writers excluded while the new, explicitly authorized recovery processes run.
- `--confirm-external-fence` and `DIRECTORY_EXTERNAL_FENCE_ASSERTION=fenced` record the operator's assertion. They do not stop processes, prove the fence, or detect a restored database. Restoring a backup can lose all changes since that backup.
- Use separately provisioned Social register-read and register-repair secrets, each at least 32 bytes and distinct from each other and the other Directory credentials. Keep them out of logs and command histories.

## Recovery sequence

1. While the external fence remains effective, restore the selected backups or prepare fresh stores and apply the owning services' migrations. Confirm the source and target stores and expected backup loss.
2. Run the **built Social operator** with its `POSTGRES_HOST`, `POSTGRES_PORT`, `POSTGRES_USER`, `POSTGRES_PASSWORD` and `POSTGRES_DB` pointed at the intended Social store. In order, invoke `node source-epoch-operator.js begin-recovery --confirm-external-fence`, then `initialize-register --confirm-external-fence`, then `enable-register-capture --confirm-external-fence`. A contradictory or clean existing register row makes initialization fail closed; investigate and reconcile it under the fence rather than bypassing the check.
3. With the external fence maintained, read the new `sourceEpoch`, `activationId` and `socialGeneration` from the Social authority using an authorized operator connection. Run the **built Directory operator** `node register-recovery-begin-operator.js --confirm-external-fence <sourceEpoch> <activationId> <socialGeneration> <new-owner-uuid> <previous-identity-json-or-absent>` with `DIRECTORY_DATABASE_URL` set to the intended Directory store. A first installation uses `absent`; recovery supplies the exact previous six-field identity. The returned object includes phase and cursor; provision **only** `sourceEpoch`, `activationId`, `socialGeneration`, `recoveryEpoch`, `owner` and `directoryGeneration` as `DIRECTORY_REGISTER_RUNTIME_IDENTITY` in an independent configuration store. Do not derive trusted runtime configuration afresh from the same restored databases.
4. Start only the newly authorized Social, Directory and worker processes under controlled access. Set Social `SOCIAL_DIRECTORY_MODE=register-only`; set Directory `DIRECTORY_MODE=register-pending-v1`; set the worker `DIRECTORY_WORKER_MODE=register-pending-v1`. Both pending runtimes need the independently provisioned identity and `DIRECTORY_EXTERNAL_FENCE_ASSERTION=fenced`; the worker needs both register secrets and Directory needs the read secret. Configure Social host/port and Directory database connectivity globally, never per town.
5. Wait for a complete baseline and a complete repeating sweep. Confirm readiness, the full eligible Social ID set against Directory contexts and blocked work, missing/failed counts, privacy withdrawals, and observed lag against the approved target. Confirm that stale identities and old processes remain excluded. A successful readiness check is not itself a complete census or proof that a future restore will be detected.
6. Record the before/after census, backup and loss window, identities/secret identifiers without secret values, fence controls, timings, failures, and reviewer decision. Release only the intended new processes and supported writers according to the deployment's reviewed controls. Continue to prevent older binaries and unauthorized direct writers from reconnecting.

The register is retained and swept repeatedly; no destructive ACK is enabled. Capture-only Social writes do not depend on Directory or Redis. The current pending path blocks provider work and returns pending/unavailable only. Its direct-writer repair is eventual and cannot reconstruct transient privacy changes that occurred between observations.

Evidence and known gaps: [S3 onboarding proof](S3-onboarding-proof.md) and [isolated Compose operating evidence](S3-compose-operating-evidence.md). Production controls, authoritative coverage and operating-scale SLO have not been verified.
