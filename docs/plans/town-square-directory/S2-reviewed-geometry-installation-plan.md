# S2 reviewed geometry installation — next implementation boundary

**Status: private installation, gated containment and boundary display implemented with isolated evidence; full acceptance remains open.** A recorded decision is retained audit evidence only. It does not install a geometry, authorize public release, or prove present Social visibility. This plan must be implemented and verified before S2 can be accepted.

1. Stage a local Census ZIP, compute its bytes and SHA-256, and use the existing bounded `readCensusBoundaryCandidate` GEOID reader against the decision's exact archive, vintage, state and layer. Reject mismatches, ambiguous or invalid geometry, and missing dependencies. The installer must own the reader and must not accept a caller-supplied polygon as proof of source identity.
2. Bind each installed geometry version durably to the decision request, exact source and Directory recovery identities, source change token and geography fingerprint. Under the established authority and town locks, re-read the current candidate and Social geography after extraction, confirm that they still match the decision and that the town is eligible, and atomically insert the version and binding. A request retry must not produce a different geometry or duplicate a version. Audit records do not themselves imply that a binding is active.
3. Reconciliation must retain readiness only for an eligible town with an exact matching binding and source token; a changed token, absence, ineligibility or missing binding resets readiness before any next read. Recovery must reset readiness and prevent an old binding from becoming active under a new recovery identity. Preserve historical evidence without reviving it. The existing register reconciler resets every town to pending, and the legacy `setBoundary` method accepts caller-provided geometry; neither is sufficient for this path.
4. A public or operator containment response must freshly revalidate the current Social source and the active Directory authority, fail closed on unavailability or mismatch, and bind the result to the installed version. Describe the unavoidable in-flight race honestly: a change after the last read can overtake a response unless an explicit cross-service ordering protocol closes it. Until the serving path and withdrawal behavior are proven, keep the public response pending and use only the approved labeled approximate-point fallback.
5. On fresh disposable stores test exact archive and GEOID matching, forged and stale decisions, changed geography even with the same token, private/deleted/restored towns, concurrent source changes and withdrawal, duplicate retries, authority rotation and recovery, holes/borders/overlap, and the Outer Banks/Kill Devil Hills distinct-ID case. Prove the actual authenticated gateway-to-Directory-to-Social path and desktop/mobile UI before calling S2 complete. No test fixtures or approximate points should be represented as verified boundaries.
