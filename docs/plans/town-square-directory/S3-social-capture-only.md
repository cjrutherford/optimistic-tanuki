# S3 Social capture-only authority — 2026-11-05

## Bounded behavior

`SOCIAL_DIRECTORY_MODE=register-only` permits covered Social community writes only after a fenced operator initializes the Social register and explicitly enables the new capture-only authority. The initializer records `registerBaselineEpoch` in the same transaction as baseline creation. Capture entry requires a matching current source epoch and an unbound, fenced authority. Writes retain the existing pre-mutation lock, coalesce into the Social register and preserve legacy outbox rows; the legacy outbox count cap does not gate this mode. Recovery takes the same lock, fences and rotates the source epoch, and invalidates the baseline marker before traversal. Existing active-mode checks, Directory startup and Social acknowledgement fences remain in place. This is not automatic onboarding or S3 acceptance.

The generated Social migration adds a nullable baseline epoch column and its down migration drops it. The implementation worker reported running migration up/down/up and the repository migration validator against a disposable database; a separate freshly created disposable PostGIS 17 database was migrated successfully during review. The Social development build, export disposition tests (8), and outbox unit tests (10) passed. The focused capture database suite passed 4 tests: baseline/phase/confirmation rejection, legacy rows and cap preservation with rollback and recovery re-entry, recovery waiting for an in-flight writer, and actual community creation, privacy update and deletion with the legacy outbox at capacity. The runtime authority rejection test populates all other local active-authority prerequisites in a rolled-back transaction while leaving phase capture-only. Identity and membership reads in the service mutation test are stubbed; no Directory service or consumer is involved.

The first independent review found no concrete blocker and requested additional phase, actual-mutation and re-entry evidence; the focused tests were expanded as described above. A second read-only independent review found no concrete regressions or unresolved objections and confirmed the expanded tests address those three gaps; it did not run the tests. An initial worker command inadvertently ran the wider Social suite and reported five failures in directory eligibility and epoch-read unit fixtures; separate focused runs reproduced four eligibility failures and one epoch-read failure because the old fixtures do not provide the current runtime authority. The two affected focused files were subsequently updated to supply explicit synthetic authority only in contract tests, with a separate assertion that the real authority provider remains unavailable. The eligibility file then passed 6/6 and the epoch-read file passed 2/2. The full Social suite was not rerun.

## Operator and recovery boundary

Before using the operator transition, stop and drain all Social and Directory workers, servers and direct writers, including older binaries; the confirmation flag is an assertion, not enforcement. An old consumer cannot interpret the now-stalled legacy stream as current coverage. A restored Social database may restore both the baseline marker and capture-only phase: local fields cannot detect this. Operators must maintain the external fence, rotate authority, reinitialize or reconcile and explicitly re-enter capture. Rollback to old binaries likewise needs a fence and authoritative reconciliation. The current test re-entry rotates a live disposable store; it is not an independent restore or rollback exercise.

Unproven: full Social writer and import coverage, direct-database writer restrictions, process restart and real stack outage, complete initialized town census, consumer authorization, delivery, receipts and cleanup, full concurrent mutation coverage, coordinated backup/restore, and public privacy lifecycle. Capture records and tombstones can grow with the number of distinct community IDs. Do not deploy or enable public data on the basis of this increment alone.

## Independent-process capture check

On a second freshly migrated disposable PostGIS database, a focused test initialized capture-only authority and retained one legacy event at the old outbox cap. It spawned one Node process using the real Social TypeORM datasource and write helper to create a town, waited for that process to exit, then spawned a separate Node process to reconnect and capture a privacy update. The final database query verified the private flag, a changed dirty register token and the unchanged legacy event count. The focused Nx test passed 1/1. A separate manual run exercised the operator commands and the same two-process sequence.

This proves persisted authorization and capture across independent short-lived helper processes. It does not restart the Social server, PostgreSQL, Directory or Redis, exercise service transport or perform a database restore. The external all-writer fence remains an operator responsibility; stale restored authority is still not self-detecting.
