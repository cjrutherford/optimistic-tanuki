## Scope and validation discipline

- Record actual apps/libs/services and changed paths at the start and end of each slice. The owners above are candidates until source and the resolved Nx graph confirm their specific dependencies. Nx project discovery succeeded using the local pnpm binary, including `client-interface`, `local-hub`, their E2E projects, and `hai-ui`; individual target configurations remain to be resolved before execution.
- Resolve project targets using Nx before choosing commands. Run the smallest failing slice first, then its affected suite. Use `NX_DAEMON=false NX_ISOLATE_PLUGINS=false` with workspace pnpm.
- Include `local-hub`/`local-hub-e2e` explicitly: TS is part of this release even though the repo's default three-client validation list omits it. Run `client-interface`, `forgeofwill`, and `business-site` broader checks when shared UI/auth changes affect them.
- Before live-stack E2E, confirm app ports and the TS origin from checked-in configuration. Respect suite-specific setup/teardown skip flags; never tear down shared services during a live-stack run. Prefer checked-in Chrome support where applicable.
- For cross-stack implementation closeout, run the delivery workflow's `pnpm run build:dev` gate in addition to relevant runtime proof. Documentation mapping alone does not need that build.
- Schema remediation follows the owning service's Nx migration-generation target, generated SQL review, fresh-database migration test, and `pnpm run validate:typeorm-migrations`.
- No prototype writes, secret/config copying, release, push, or deployment is implied by this mapping. Evaluation reads the confirmed local checkout.
- Keep DF-001–DF-005 visible. Reputation implementation, payments/business tiers, federation implementation, per-community forums, and Daylight expansion remain deferred unless a separately documented scope decision changes them.

## End-of-slice findings report

Save detailed evidence beside the owning slice and summarize it to the user before the next slice:

1. **Status:** `ACCEPTED`, `VERIFYING`, `GAP FOUND`, `DEFERRED`, or `BLOCKED`, with the reason. Use the master vocabulary; acceptance requires every criterion's evidence.
2. **Findings:** stable finding IDs, severity, affected workflow/owner, expected versus observed behavior, and concrete source/runtime evidence. Separate verified findings from hypotheses.
3. **Changes:** affected apps/libs/services and focused remediation; note anything deliberately deferred and its DF entry.
4. **Verification:** exact commands, result, environment/commit, user roles, viewports, screenshots/source traces, and checks not run. Source presence or a green build alone is insufficient.
5. **Remaining work:** unresolved P0/P1, external decisions/dependencies, known limits, claim dispositions affected, and the next slice.

Synchronize status/evidence in `MASTER-AUDIT.md`, the slice, and the deferred register. Keep one authoritative detailed report per slice and link it rather than copying growing evidence tables.
