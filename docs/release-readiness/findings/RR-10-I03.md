**Stale initial route-response repair (2026-10-13):** Review of RR10-V01 found that `loadCommunityBySlug` and `loadUserCommunitiesChat` started version tracking but did not retain a request generation or recheck it after awaited REST calls. A delayed earlier route/profile response could therefore replace the selected community, room, history, loading state, or error after navigation or profile change. The component now gives each initial community load a generation and checks it after community-list/slug, chat-room, and chat-history calls; it also guards owner room-creation recovery and ignores stale errors/finally updates. Profile changes invalidate the generation and clear the previous community state.

Three delayed-response regressions were run before the fix and failed for the expected reasons: an old slug result replaced the new community, an old request error overwrote current error state, and an old user-community list repopulated state after profile change. ## Findings and repair

The permission resolver previously collapsed every failure into an empty permission list, making a transient service failure indistinguishable from a legitimate denial. Forum list errors could also render the empty state while displaying an error. The local development stack had a separate reliability issue: Nx development builds removed and recreated bind-mounted output directories while nodemon processes used those directories as their working directory. This produced `process.cwd`/`uv_cwd ENOENT` crashes in auth, profile, forum, and chat-collector services. This is a local development lifecycle issue, not evidence of product capacity or production behavior.

The bounded repair distinguishes resolver outcomes: 401 follows the existing login/session-expiry flow; 403 displays a read-only denied state with authoring hidden; transient failures show a retryable unavailable state. Topic, topic-thread-list, thread, and post-list failures each retain a visible reason and relevant retry control. Empty states appear only after a successful empty response, and a failed deep link clears stale selected content. Nx development webpack defaults now preserve existing output directories; production behavior is unchanged.

**Towne Square tablet message fan-out finding (2026-10-13; repair and live proof):** RR06 tablet diagnosis found that the legacy `MessagesComponent.messageSubmitted` path sent through REST without live gateway fan-out, and the malformed `:3300` socket fallback yielded no websocket connection/events while REST history returned 200. The message component now uses the shared stable-ID submission/ACK path; `apps/local-hub/src/app/app.config.ts` preserves configured absolute socket URLs and otherwise uses the same-origin proxy. A second regression was fixed in `apps/local-hub/src/server.ts`: Express strips the `/socket.io` mount prefix before proxying, so the target must include `/socket.io`; `createSocketIoProxyOptions` now constructs that target and the integration test observes the complete polling path at the gateway. REST message persistence now passes the returned persisted message to the existing session/membership-guarded `ChatGateway.notifyPersistedMessage`, shared with WebSocket writes. The 2026-10-13 tablet V01 case passed buyer REST send → seller open-socket message/conversation events → seller visible receipt/reply → sender/readback, followed by exact fixture cleanup (Nx run `vySHWEAARr`, 1 case/23 s; see [RR10-V01](./RR-10-V01.md)). The earlier 35-suite/384-test and `4H9bHBPRwW` build are historical; current post-refactor results are recorded in V01. Independent review of the latest proxy and REST fan-out repairs is GO. This proves the bounded user path, not capacity or a latency SLO.
