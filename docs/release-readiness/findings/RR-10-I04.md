## Scope and confirmed behavior

The slice covers client-interface Messages and the shared OT/TS community-chat route. Forge/project callers intentionally retain the existing legacy fire-and-forget contract for compatibility; source review confirms those consumers still clear text eagerly on submission. Their rejected-draft recovery is outside this slice and has a separate follow-up in [DF-006](../DEFERRED-FEATURES.md#df-006--acknowledged-chat-submission-and-rejected-draft-recovery-for-legacy-consumers). That behavior is not described as unknown and does not block the bounded OT/TS acceptance.

The shared chat client offers an explicit acknowledged send path while preserving legacy behavior for callers that do not opt in. The gateway acknowledges only after collector persistence, returns sanitized status-aware failures, and rejects a persistence receipt whose stable ID does not match the submission. The composer disables duplicate submission while pending, retains the exact rejected draft and stable message ID for a deliberate retry, and clears only the exact text associated with a successful acknowledgement. A late acknowledgement cannot clear subsequently edited text. There is no automatic resend and no exactly-once delivery claim. Stable message IDs remain UUID-shaped when `crypto.randomUUID` is unavailable.

The collector handles a simultaneous same-ID insert by rereading the durable row after a unique-key conflict and comparing sender, conversation, and content; an incompatible record remains a conflict. A live sequential retry initially returned an empty `messages` receipt because the existing-ID branch omitted the durable history. The branch now loads the stored history only after current conversation authorization and payload equality; the conflicting-ID path remains 409. Focused tests cover receipt contents, authorization before duplicate lookup, and mismatched payload rejection. The corrected live replay of the retained ID passed, as did conflicting-payload rejection and concurrent same-ID persistence. Reconnect reloads authorized history. Socket arrivals during a pending history request are merged immediately before state replacement, and revision/profile/community guards discard results from a prior user or route. An empty socket conversation snapshot now rechecks a REST-loaded room through the authenticated conversation endpoint: a matching 200 retains the current room/history, 403 clears with the approved-membership message, 401 asks the user to sign in, 404 reports the missing room, and other errors fail closed with a temporary verification message. The reauthorization result is guarded by history version, profile, community and room. Broader in-flight route REST loads still lack equivalent guards and are scheduled as RR10-I04-R01.

The internal cleanup command is TCP-only and guarded by runtime identifier/type checks, owner conversation type, exact community and scope, the community's current recorded owner, approved owner membership, and a live-record conditional update. It soft-deletes only the conversation and retains message rows. The existing weak HTTP delete behavior remains untouched. No public delete route was added, and the internal TCP payload is not claimed to be cryptographically authenticated.
