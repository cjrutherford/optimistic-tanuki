# D03 — Assets deletion and active-reader custody

Status: verified local OT/TS owner adapter, 2026-10-25. Scope: `client-interface`, `local-hub`, and their Assets owner. This is an owner receipt, not completion of account deletion.

The internal owner accepts only a signed Assets grant for the literal requested action and obtains the frozen account/profile scope from Authentication. Producer fences drain existing writes, reject later writes using OLD and NEW identity participation, and preserve counterpart assets. Fencing marks owned metadata pending-delete before storage removal. The owner releases database locks around storage I/O, revalidates authority and row custody before metadata deletion, and retains retry metadata when removal fails. Keys remain available for recovery.

Local purge requires the exact reserved asset path, rejects symlinks and hard links, bounds directory traversal, and independently checks directory absence. The network adapter derives its exact normalized key from the reservation and requires the existing version/delete-marker purge and readback receipt; this does not qualify a live S3 deployment.

Authenticated media reads hold a separate shared profile read lease. Deletion takes the exclusive read drain after installing producer fences. Plaintext is authenticated into an exclusive private file unlinked before source consumption, then retained only through its file descriptor. Closing a reader releases its descriptor before its database lease. Process death releases both. Unverified cleanup keeps the lease; legacy named plaintext or quarantined spool custody blocks deletion verification. Ordinary producer writes use a separate lock namespace and do not wait for media readers.

Guardian history is preserved under the approved N04 policy. Matched account/profile identities, asset references and private changed-field context are erased; unmatched counterpart identities remain. Audit work carries the trusted operation context and runs after owner locks release.
