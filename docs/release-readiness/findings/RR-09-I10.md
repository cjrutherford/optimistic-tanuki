# RR09-I10 — Immediate permission-cache invalidation for role assignments

**Status:** PLANNED — required security repair before V01 and release.

**Finding:** During the approved RR09-I09 controlled report flow, the verifier assigned the existing `client_interface_operator` role to the retained I04 reporter profile, submitted one report and requested its dismissal. Exact cleanup removed that role assignment and readback returned the reporter to its five-role baseline. A direct uncached authorization check denied report review, while the gateway's cached operator-report GET continued to return HTTP 200. A Nodemon reload reset the in-memory cache, after which the operator route returned 403. Final read-only state at 2026-10-11 19:22:15Z again showed baseline roles, no operator assignment, direct denial, and operator GET 403 without writes/restart; cache-wait interval was zero. Natural TTL expiry was not observed, and neither the reload nor final state demonstrates immediate invalidation. The first API dismissal response did not match the database: exact readback still showed `pending` and no `content_moderation_action` row. A targeted current-source Social build/restart and authorized PUT on that same existing report row corrected the discrepancy; PostgreSQL now confirms `dismissed` and one `report_status` action row. This initial runtime mismatch is resolved and recorded in I09. The assignment DELETE itself also initially returned HTTP 500 after deletion because the permissions RPC emitted no acknowledgement; that response-contract defect is repaired and tracked in [I09](./RR-09-I09.md). The remaining stale positive authorization is a separate security finding.

**Required scope:** Ensure role assignment and unassignment invalidate the affected profile's authorization cache immediately. The permissions RPC must provide the affected `profileId` to the gateway/cache invalidation path. Preserve existing role policy and permission evaluation; do not mask stale authorization with a process restart or wait for TTL expiry.

**Acceptance evidence:** Add focused tests proving role grant becomes effective immediately and role revoke is denied immediately through the same gateway authorization path, including the report-review read route used in I09. Verify the exact profile and assignment readback, affected tests/lint/build, current-source runtime refresh, and independent review. Do not create another report record for this repair; use controlled role fixtures with exact assignment cleanup/readback.

**Release gate:** RR09-I10 must pass before RR09-V01 acceptance and release. RR-09 remains GAP FOUND until I10 and all V01 criteria pass.
