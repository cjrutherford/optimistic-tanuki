**Required scope:** Ensure role assignment and unassignment invalidate the affected profile's authorization cache immediately. The permissions RPC must provide the affected `profileId` to the gateway/cache invalidation path. Preserve existing role policy and permission evaluation; do not mask stale authorization with a process restart or wait for TTL expiry.

**Implemented boundary:** The gateway wraps only its configured permissions `ClientProxy`, covering all gateway consumers of that token, including REST endpoints and community, workspace, finance, and learning workflows. Successful assignments use the request profile ID; exact unassignment returns `profileId` and `changed`; target-scoped unassignment returns the affected profile; bulk mutation returns its affected profile IDs. The gateway waits for invalidation before forwarding a success acknowledgement. An absent exact assignment remains idempotent and returns success with `profileId: null`; the gateway performs a fenced clear of the permissions cache because the affected profile is unknown. Ambiguous mutation errors evict known request profiles; exact-unassignment transport errors perform a fenced permissions-cache clear before the original error is propagated.

Both `PermissionsGuard` and `PermissionsProxyService` now use a profile-epoch-fenced cache lookup. A lookup that overlaps invalidation retries against the permissions service instead of returning or storing its earlier result. Concurrent lookups await the invalidation barrier without blocking the event loop. Cache deletion errors propagate; failed deletion keeps permission-cache reads/writes bypassed until a successful namespaced clear. The Redis provider rejects empty or glob-bearing key prefixes, and clear only deletes keys in its configured permissions-cache namespace. These safeguards apply to role assignment and unassignment; they do not invalidate cached decisions after role-definition or role-permission edits, which remain outside I10's bounded scope and require separate policy-change invalidation work if advertised as immediate.

The epoch fence is process-local. With the default memory provider, gateway authorization cache state is single-instance. A shared Redis cache allows successful mutation invalidation to delete shared profile keys, but an in-flight permission lookup on a different gateway replica can still repopulate after that deletion because I10 does not add cross-process generation coordination. Multi-replica fencing requires a separate design and must not be claimed here.
