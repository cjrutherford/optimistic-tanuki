# RR09-I04 — OT feed: edit own post

**Status:** ACCEPTED — bounded OT feed own-post editing repair, including selected-profile authorization and recoverable save behavior. RR-09 remains GAP FOUND; RR09-I05 and RR09-V01 remain required before RR-10.

## Trigger and reproduction

The user reported that signed-in users could not edit their own posts directly from the feed. In the controlled OT stack, the owner-path menu, exact prefill, cancel, successful save, and reload persistence worked for the selected owner profile. The report is therefore not a universal failure of the owner path.

A controlled update failure exposed a confirmed recoverability defect: the shared post editor closed when it emitted `postUpdated`, before the feed's HTTP request completed. When the request returned 500, the draft was no longer visible and the owner could not retry from the editor. The feed also allowed the rejected request to escape its handler without accessible, row-specific feedback. The final live run proves the repaired editor preserves the draft and alert and allows one successful retry.

The first live alternate-profile denial probe exposed an additional error-contract defect: the social service rejected profile B's attempt to edit profile A's post before any write, but threw a plain `Error`, so the gateway returned 500 instead of 403. The owning service now returns its established structured 403 RPC error for both personal-profile and community-post authorization denials; the existing gateway exception filter maps that status to HTTP 403. The final live run verifies the 403 and unchanged row; service tests assert no repository mutation.

Source review also found two authorization/session defects required for selected-profile editing. `/authentication/issue` accepted a caller-supplied profile ID without verifying its ownership or registered app scope. The profile-creation controller accepted an arbitrary body `userId` and then requested a token for that identity. Both now validate against the authenticated user before issuing a session or mutating profile data. A switched cookie's session identity is read back and checked before it is published to client state; a mismatch leaves the previous verified identity in place while rollback runs.

## Implementation

- The shared post component now supports an opt-in controlled-save lifecycle. The OT feed keeps the editor visible while saving and after failure, disables duplicate submissions while the request is pending, exposes a row-specific alert, and closes only after it receives the authoritative updated row. Existing non-OT consumers retain the legacy close-on-submit behavior.
- OT profile selection reuses `lib-profile-selector`. It lists owned client-interface and global profiles, keeps the old selection checked while a switch is pending, and commits the new selection only after the gateway issues and the browser verifies a cookie session for the same user and requested profile. Concurrent switches are locked; failed switches restore the old session or end it with a clear error if rollback cannot be verified.
- Login, registration, session restoration, and the profile guard now honor the verified JWT profile ID instead of selecting the first returned profile.
- OT-created profiles explicitly use `appScope: client-interface` and activate through the verified cookie flow; legacy bearer tokens returned by the create endpoint are not installed in the browser.
- Gateway profile creation rejects missing, empty, or mismatched body `userId` before profile creation or token issuance. The `/authentication/issue` controller validates requested profile ownership and current registered app scope before issuing a session.
