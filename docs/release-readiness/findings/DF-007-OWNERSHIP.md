The [machine-readable catalog](../evidence/df-007/ownership-catalog.json) covers all 166 tracked TypeORM entity files under `apps/` and `libs/` at this revision. Implicit table names remain unresolved. It also includes the two migration-backed compliance-audit tables. This catalog identifies schemas to review; it does not prove live schema or ownership semantics.

The 2026-10-20 refresh verified all 167 previously cataloged source hashes (165 entity files plus two migration-only sources) unchanged and found exactly one added tracked entity: Authentication `AccountExportJobEntity` (`account_export_jobs`). Its `accountId` is an account/job scope key. The accepted Authentication owner already captures bounded, sanitized job status/summary/error metadata through its `exportJob` source; internal idempotency and lease-owner values are omitted by that projection. The refresh records this structural delta and its hash in the [reconciliation receipt](../evidence/df-007/ownership-reconciliation-2026-10-20.json). This refresh does not establish semantic completeness, runtime registration, or non-ORM coverage; the catalog remains a heuristic.

## Highest-priority boundaries and hazards

- **Permissions:** `RoleAssignment` is profile-linked state (`profileId`, `roleId`, `appScopeId`, optional target); it is account-scoped. `Role`, `Permission`, and `AppScope` are shared definitions and must not be removed as if owned by one account. `Permission.targetId` can represent a profile target even though the property name does not identify that semantics. See [role assignment entity](../../../apps/permissions/src/role-assignments/entities/role-assignment.entity.ts:13) and [permission entity](../../../apps/permissions/src/permissions/entities/permission.entity.ts:15).
- **Social:** 33 entities include author/user/profile records, social graph and interaction rows, search/presence/view state, guardian audits/grants, and community ownership/membership/election records. Posts own comments, attachments, polls, votes/reactions and other sidecars through relations; community-owned content can contain other users’ contributions. Deleting one user’s rows needs content-specific ownership rules and account placeholders while preserving others’ contributions. `Community.ownerId`, `ownerProfileId`, `managerProfileId` and membership rows also make ownership transfer/continuity unresolved. See [Post](../../../apps/social/src/entities/post.entity.ts:25), [Community](../../../apps/social/src/entities/community.entity.ts:26), and [CommunityMember](../../../apps/social/src/entities/community-member.entity.ts:27).
- **Forum:** `Topic`, `Thread`, and `ForumPost` each carry `userId/profileId`; posts link to threads and threads to topics, while reports/moderation actions carry reporter or actor profile references. Parent deletion could remove other users’ posts. Determine whether to remove only the account’s authored rows and retain a deleted-account placeholder. See [ForumPost](../../../apps/forum/src/entities/forum-post.entity.ts:12), [Thread](../../../apps/forum/src/entities/thread.entity.ts:11), and [Topic](../../../apps/forum/src/entities/topic.entity.ts:4).
- **Chat:** conversation participants are a text array; messages separately store `senderId` and `recipients`. Current `isDeleted` is conversation-level and can hide everyone’s conversation. Deletion must remove the departing account’s messages/content, update participant references, preserve other people’s messages, and leave the approved deleted-account placeholder. See [Conversation](../../../apps/chat-collector/src/app/entities/conversation.entity.ts:10) and [Message](../../../apps/chat-collector/src/app/entities/message.entity.ts:11).
- **Classifieds:** each local-hub ad carries `profileId/userId`, description, price, community and `imageUrls` as a string array. Ads are account content; image URLs do not establish ownership or deletion of the underlying bytes. See [ClassifiedAdEntity](../../../apps/classifieds/src/app/entities/classified-ad.entity.ts:14).
- **Assets and video:** Assets stores `profileId`, `storagePath`, storage strategy, audience restrictions and lifecycle state. Its service supports local/remote block storage, idempotent pending-delete retries, and authenticated media reads; raw path deletion alone is unsafe. Social attachment rows refer to `filePath`; community/event assets and Videos have asset IDs. Video records have `assetId`, `sourceAssetId`, `playbackAssetId`, `hlsManifestAssetId`, and `thumbnailAssetId`; Channels and views/subscriptions carry profile/user IDs. Classifieds and payment rows also carry URLs. These reference edges must be resolved before media can be deleted/exported. See [AssetEntity](../../../apps/assets/src/entities/asset.entity.ts:12), [asset lifecycle](../../../apps/assets/src/app/app.service.ts:343), [Video](../../../apps/videos/src/entities/video.entity.ts:12), and [social Attachment](../../../apps/social/src/entities/attachment.entity.ts:21).
- **App membership and workspaces:** app instances/memberships and workspace rows have owner/user/profile keys. Decide whether account exit removes membership, transfers shared workspace ownership, or removes workspace-owned data; do not delete the shared workspace solely because its creator leaves. See [AppMembershipEntity](../../../apps/app-configurator/src/configurations/entities/app-membership.entity.ts:27) and [Workspace](../../../apps/workspace/src/entities/workspace.entity.ts:15).
- **Payments, finance, billing, store:** records expose user/profile, buyer/seller, bank/provider account, tenant/account, orders, invoices, subscriptions, donations, payouts and transaction fields. `finance` also contains encrypted vault/bank material. These are sensitive account-linked candidates; no legal, provider, or backup retention exception has been authorized. Exact account mapping, subscription cancellation, provider deletion, and readback are unresolved, so this report does not propose retaining any data.
- **Other product data:** blogging has `ownerId`, `authorId`, `organizerId`; project-planning has free-form `owner`, `members`, `createdBy`, `updatedBy`, `deletedBy`, `assignee`, and `profileId`; learning has user/profile, offering owners/co-editors, and actor fields; wellness uses profile IDs; Telos docs include profile/project summaries; lead-tracker includes actor and recipient-email fields. Civic content is tenant-scoped without user/profile IDs. System configurator saved configurations/orders/quotes lack direct identity keys. These are unresolved until service owner mapping and references are established, not exclusions.
- **Audit and security state:** Authentication, profile, assets and social have guardian activity/permission/audit entities. Compliance-audit has tenant-keyed `compliance_audit_logs` and `vault_documents` in migrations, and `business-security` entities. `compliance_audit_logs` contains hash-chain fields and may be treated as append-only; whether tenant equals account/profile and how owner-mandated deletion/90-day purge applies is unresolved. Also inventory Redis/session stores, file caches, gateway telemetry, provider state and backups; they are outside the entity catalog. See [compliance audit migration](../../../apps/compliance-audit/migrations/1790340457168-initial.ts:8), [vault document migration](../../../apps/compliance-audit/migrations/1790347292239-vault-doc-schema.ts:24), and [tenant resolver](../../../apps/gateway/src/security/vault-tenant-resolver.service.ts:28).

## Required completion rule

The coordinator’s required participant set must be generated from actual service registration/ownership inventory, not from the OT/TS frontend list. For every candidate owner above, require an explicit export/delete/readback acknowledgement or a reviewed zero-data result. If any participant is unavailable, unmapped, incomplete, or cannot prove the final readback, the user-visible operation must remain pending/failed and must not return a complete export or claim deletion success. Do not serialize credential/key/session secrets as export data. The account’s authentication principal should be revoked/deactivated only after the deletion workflow has durable, idempotent progress and can safely resume.

## Inventory limitations and drift guard

This inventory uses the source files tracked by Git at the stated revision. It does not inspect database rows, connect to databases, prove entity registration in every runtime composition, derive physical table names for implicit `@Entity()` declarations, or establish FK/cascade behavior. It also does not fully discover raw SQL, migration-only schemas outside the named compliance-audit tables, browser storage, Redis/cache contents, external providers, object-store backups, or log pipelines. The untracked directory-service work and the root report/plan files were excluded from this tracked-source catalog.

A CI drift guard should regenerate this JSON from `git ls-files apps libs` and TypeORM entity registrations, compare the entity set, class/table/primary-key/field/relation metadata and source hashes, and fail whenever an entity, ownership-shaped field, media-reference field, tenant/account key, migration-only table, or participant mapping changes without an updated classification. Separately compare runtime TypeORM metadata and migration schemas for each registered service. This inventory is source evidence for planning; it is not an acceptance proof for DF-007.
