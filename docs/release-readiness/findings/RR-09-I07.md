# RR09-I07 — Floating chat keyboard access and responsive action clearance

**Status:** PLANNED — bounded implementation checkpoint from the in-progress RR09-V01 verification (2026-10-11). RR-09 remains GAP FOUND; V01 has not passed.
**Position:** Required after the V01 finding and before V01 can pass / RR-09 can be accepted.
**Owner:** `apps/client-interface` floating chat control and its focused browser verification.

## Confirmed V01 finding

The V01 system-Chrome diagnostic found that the OT floating chat control is not keyboard reachable. After 120 actual Tab presses, focus did not reach `.chat-floating-button`. Its accessibility snapshot exposed only generic text (`💬 Messages`); the element is a clickable `div` with no role, `tabindex`, or accessible label, and it has no landmark ancestor. Enter activation was not attempted because the control was not focusable. This is a keyboard and accessible-name failure, not an Axe-only inference.

The same stable rendered-point grid confirmed partial occlusion of the community-create form actions by the fixed chat control. It did not find an intersection with the image-upload card:

| Viewport and operated theme | Affected action  | Measured intersection | Samples hitting chat |
| --------------------------- | ---------------- | --------------------- | -------------------- |
| 320×740, light and dark     | Cancel           | 105.91×20.39 px       | 24/25                |
| 320×740, light and dark     | Create Community | 105.91×26.42 px       | 24/25                |
| 375×812, light and dark     | Create Community | 105.91×41.20 px       | 25/25                |
| 1280×633, light and dark    | Create Community | 59.89×13.33 px        | 22/25                |

No target intersection was observed at 768×1024 or 1440×900. These are measured partial intersections; the report does not claim the whole action is blocked or that the upload card is obscured.

The diagnostic journal is `.runtime-artifacts/rr09/v01/chat-overlap.jsonl` (mode 0600; SHA-256 `4e8e7703331d6ab13c24254a61b28b8fc7b66afda459a29664a9bf75577ae8e8`); ten screenshots are in its sibling `screenshots/` directory. The diagnostic harness SHA-256 is `7aa317146941df5356bcb63a820458c5be0011185dbf23fd6402a25623f5f931`. The app theme was restored. No community or post fixture was created by this check. This evidence supports a planned repair only; no V01 acceptance or repair is claimed.

## Bounded implementation and acceptance

Repair the floating chat entry point so that it:

- is reachable and visibly focused in natural keyboard order, activates with Enter and Space, and exposes an appropriate accessible name and expanded/collapsed state;
- has an appropriate semantic context without creating a misleading or redundant landmark;
- opens and closes the chat panel with predictable focus movement and restoration;
- clears the measured Cancel/Create Community target intersections at 320×740, 375×812, and 1280×633 in both operated themes while retaining usable placement at 768×1024 and 1440×900.

Rerun the focused semantic/focus checks and the complete five-viewport, two-theme point-hit grid after the source freeze. Verify focus visibility and panel focus behavior, capture the relevant screenshots and stable rendered geometry, and check that all tested form actions receive hits at their actionable areas. Keep the overlap correction limited to the floating chat/form-action collision; the upload card itself had no intersection. Run affected tests/lint/build, refresh only the authorized existing stack, confirm no audit fixture remains, and obtain independent review before closing I07.

RR09-V01 remains open until the I07 repair is independently verified and all other V01 criteria pass. Any further confirmed defects must receive their own numbered checkpoint before RR-09 acceptance.
