## Confirmed source finding

### RR10-F01 — authenticated media retrieval previously rejected objects above 25 MiB and materialized whole objects

**Severity:** P1 — required large-media capability and bounded-resource behavior are missing.
**Baseline evidence:** At the audit baseline, `apps/assets/src/app/internal-media.service.ts` rejected stored data above 25 MiB plus 64 KiB and buffered the entire authenticated plaintext before slicing a range; local storage decrypted whole envelopes into a `Buffer`, and S3 concatenated all chunks into a `Buffer`. The OTENV1 format uses one AES-256-GCM authentication tag for the full envelope, so partial plaintext cannot safely be released before final tag verification. RR10-I01 retains this format and implements a private verified spool before response.

**Upload boundary:** At baseline, content and `sourcePath` were materialized before size validation, and video had no explicit `maxSizeBytes`. RR10-I01 now prechecks base64 length and opens/stat-checks the same no-follow source descriptor before bounded streaming; it adds the 25 MiB video limit and client-side FileReader preflight in the shared OT, social, classified, and Towne Square paths changed in this slice. Upload ceilings are 20 MiB for image/audio and 25 MiB for video/documents. Scanning remains fail-closed and buffer-based; streaming antivirus and uploads above these limits are not supported or claimed.

**Transport considerations:** RR10-I01 adds fetch deadlines, request/response cancellation, pipeline backpressure, bounded spool quota, cleanup and fail-closed errors at the gateway and internal media controller. Retrieval defaults are 1 GiB per object, two concurrent reads, and 2 GiB of spool per process; these are per-process bounds, not cluster-wide quotas.

**Implementation and bounded proof:** RR10-I01 is implemented in this branch. Its isolated local HTTP harness proves 30 MiB full and range fidelity, authorization before storage access, tamper/wrong-key denial with empty response, and client-abort spool cleanup. A separate child process streams a 96 MiB object through the spool with measured RSS delta 28.98 MiB, exact 100,663,296-byte spool high-water, and cleanup. Controlled S3-body success/abort, source-path size/growth rejection, gateway HTTP proxy, and focused UI upload-preflight tests also pass. The HTTP harness directly invokes `InternalMediaController` with metadata/config test doubles; the RSS child exercises the spool service directly. Neither proves Nest/deployed composition, live S3, concurrent resource bounds, or real app-level media rendering. Those remain in RR10-I01-V01.

The shared chat client now supports an explicit acknowledged submission path while retaining the legacy fire-and-forget contract for callers that do not opt in. The client-interface Messages page and shared OT/TS community-chat route opt into acknowledgements. The gateway acknowledges only after collector persistence, returns sanitized status-aware failures, and rejects mismatched persistence receipts. The composer holds the active draft while a send is pending, preserves rejected text and its stable message ID for deliberate retry, ignores late acknowledgements when the draft has since changed, and prevents a second submission while pending. Stable IDs remain UUID-shaped in browsers without `crypto.randomUUID`; the collector resolves simultaneous duplicate inserts by rereading and comparing the durable row. No automatic resend or exactly-once delivery claim is made.

Reconnect history is reloaded through the current authorized conversation path. Socket messages arriving while history is pending are merged immediately before state replacement, while profile/community revisions discard stale snapshots after identity or route changes. On an empty conversation snapshot, the community-chat view rechecks an already REST-loaded room through the authenticated conversation endpoint and keeps its current history only when the server confirms that same conversation. It clears cached history on 403, asks the user to sign in on 401, reports missing rooms on 404, and fails closed with a temporary verification error for other transport failures. This reauthorization result is guarded by the current history version, profile, community, and room. Initial community/room/history REST loads now also use a community-load generation guard; delayed slug success/error and old membership-list responses are covered by passing regressions, with independent source review GO. Internal cleanup is a guarded TCP command for an owned, live COMMUNITY conversation with exact community, scope, current recorded owner, and approved owner membership checks; it conditionally soft-deletes only the conversation and retains messages.
