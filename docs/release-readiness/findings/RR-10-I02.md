# RR10-I02 — Forum parent-delete authorization and retention

**Status:** IMPLEMENTED — bounded API matrix PASS; independent source review GO. **RR-10 remains GAP FOUND and NOT ACCEPTED.** The browser UI delete flow was not exercised; verification used authenticated HTTP cookie sessions.

## Finding and decision

RR08-A02 observed gateway `403` responses when ordinary forum authors attempted to delete their own topic or thread. Source tracing found the cause: the owning service already enforced exact `userId`, `profileId`, app-scope, readability, and author checks, but the seeded `forum_user` role did not receive either `forum.topic.delete` or `forum.thread.delete`. The gateway requires those permissions before sending the request to the forum service.

The product decision for this slice is author-only deletion. Registered forum authors may attempt to delete their own content. Moderators and other users receive no author bypass; ownership still requires matching user and profile in the requested scope. Parent rows with descendants are retained and return HTTP 409 with an actionable message. No descendants are cascaded or erased. The existing foreign-key behavior remains `NO ACTION`, and a concurrent child insert that triggers PostgreSQL `23503` also maps to 409. Missing or already-deleted rows return HTTP 404.

## Changes

- Added only `forum.topic.delete` and `forum.thread.delete` to the existing `forum_user` seed associations. No create-topic permission, moderator privilege, schema change, or role-assignment change was added.
- Added topic/thread service checks that refuse non-empty parent deletion and map foreign-key races to 409 without masking unrelated errors.
- Added regression coverage for seed scope, same-profile/different-user denial, wrong-app-scope hiding, non-empty parent retention, and FK-race mapping.
- Seeded through the existing dev permissions container twice. The first run added one association for each delete permission; the second completed successfully. A read-only database query after both runs showed exactly one `forum_user` association for each permission. The permissions cache is in-memory, so only `ot_gateway` was restarted to refresh its cached denials.
