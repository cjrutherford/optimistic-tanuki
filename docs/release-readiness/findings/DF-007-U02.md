# U02 — Deletion confirmation and receipt recovery

Status: **VERIFIED LOCAL**, 2026-10-26. Classification: **COMPLETE-local**.
Scope: OT `client-interface`, TS `local-hub`, and their required shared services.

The shared confirmation displays the account and consequences, requires exact
`DELETE`, and leaves the account intact when cancelled. Preparation validates
a same-app session without accepting deletion. Auth signs a seven-day receipt
bound to a future operation ID, request ID, hashed account subject and app.
The browser saves it before dispatching acceptance and hands off to the public
receipt page before awaiting the response. Acceptance revalidates the session
and signed binding; a receipt alone cannot initiate deletion or obtain owner grants.

The real browser proof opened/cancelled confirmation in both products, checked
keyboard focus restoration and dialog accessibility, then accepted the shared
account's deletion from TS. The genuine twelve-owner coordinator was killed and
restarted while a media read held its lease. Both original app sessions were
denied. Receipt-only UI retries exercised real scope/custody failures, and
recovery completed after a real Auth delete fault following Profile finalization.
The receipt page worked after revocation, reload and manual receipt restoration.
Replacing the cookie with a different account left that session valid and did
not change the receipt's subject. Units additionally cover malformed/cross-app
receipts, changed accounts, storage failure, lost responses and minimal ledger binding.

TS SSR previously matched `/account-deletion` through its `/account` protection
prefix. A focused red/green test established the exact public-route exception
while retaining account-page protection; all six owning tests pass.

The minimal receipt intentionally survives session reset in app-specific session
storage and can be copied privately. It contains no raw account/profile ID,
name, email, session token or account key. It is sent in a header, never a URL.
Expiry/loss does not cancel cleanup; the UI explains downloads, backups and
provider-held data remain separate. The shared signing secret must be non-default,
at least 32 characters and consistent across Auth replicas.
