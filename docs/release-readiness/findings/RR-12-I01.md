## Setup constraints and non-passing attempts

The first OT registration/profile attempt reached registration and login but `/api/profile` returned 404 because the private gateway composition omitted dependencies required to register `ProfileController`. After adding the two dependencies and unused private endpoints, the checked desktop and mobile journeys passed. The feed audience case first timed out before its initial card assertion because the host could not reach the client's social WebSocket on port 3301; the measured REST fallback arrived after the five-second assertion. Publishing the exact socket port on loopback corrected the runtime configuration; the same checked case then passed. This was a configuration failure, not a product-source change.

The initial TS classified diagnostic received the configured “community owner permissions are not configured” error. Running the checked permission seed against the isolated DB supplied the default owner roles; the diagnostic then passed. Initial registration failures from authentication logged `EAI_AGAIN db`; a PostgreSQL recreation had lost the manual alias, so the private Compose override declared the `db` alias. Authentication then resolved and the buyer/seller case passed. These are local fresh-stack bootstrap constraints, not evidence of a production authorization defect.

Two additional fixture-dependent forum cases that expected preseeded public topic titles failed against the intentionally fresh DB because those topic fixtures were absent. They were not counted as product failures or matrix passes; the self-seeding forum authoring case above passed. The one earlier standalone API feed diagnostic created a uniquely owned post outside a checked test's `finally`; it remained in the disposable private DB and was removed with that project volume. All other case-owned posts, listings, communities, assets, memberships, and direct conversations were removed by their checked exact-ID cleanup/readback or by the private-volume teardown. Controlled registration accounts were not API-deleted; physical removal of the private DB volume removed them.

No application source was changed for I01. No production writes/deploys, provider/email delivery, or external RPC calls were made. Both I01-owned Compose projects (`rr12-i01` and its earlier `rr12-i01-private` diagnostic project), their containers, volumes, and networks were removed after preserving the sanitized receipt. A sorted container ID/name/port snapshot of all non-I01 containers was identical immediately before and after teardown.
