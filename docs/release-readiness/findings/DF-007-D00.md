# D00 — durable deletion control and write fence

Status: **VERIFIED LOCAL OT/TS CONTROL FOUNDATION** (2026-10-24). The next owner slice is D01. Full account deletion remains unavailable.

Deletion acceptance validates the current OT/TS session, derives the account identity from it, and rejects supplied account IDs. A separate durable operation ledger serializes account-wide idempotency. It survives removal of the user row and preserves an immutable account hash as its permanent fence. Acceptance installs the Authentication database fence and revokes that account's persisted sessions in the same transaction. Root user identities and keys remain available for dependent cleanup until D26.

Database triggers on Authentication's eight data tables lock account/profile identities for both OLD and NEW rows. Fence installation waits for prior writers; later credential, session, provider and work-store writes fail. A trusted deletion transaction can perform cleanup under the matching operation ID. The shared generator supports scalar, JSON-array and CSV identities; each later owner must register its own proven field policy and migration.

Owner grants are signed bearer capabilities bound to the operation, account, app, owner, action, attempt and current lease. Validation checks the live ledger independently of a user session. Issuance, Profile scope recording and acknowledgement are internal coordinator methods, not public RPCs. Owners must check their own literal owner/action before executing. Erasure grants remain blocked until all twelve owner fences acknowledge. Only Profile can establish the fixed profile/legacy identity sets. No terminal completion method is introduced here.

The shared placeholder projects `Deleted account` without user/profile IDs or avatar data. Its nil UUID storage sentinel cannot authenticate. Owner adapters must preserve counterpart content; conversation-specific mapping remains in those existing slices. The ledger and hashed write-fence tables are operational deletion stores, excluded from portable content export; raw account/profile scope is retained only while dependent attribution work needs it.
