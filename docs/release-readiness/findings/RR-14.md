## Decision

`retumbl` contains a substantial reputation and trust-evidence prototype, beyond the original in-memory sketch. Its current durable path evaluates an instance's local view of remote actors and domains, combines local reports with signed cross-instance attestations, records moderation cases and audit events, and applies bounded reversible score penalties. Local vouches can affect recommendations; operator blocks can override scores. This is an anti-abuse and federation-ingress policy mechanism, not user reputation, moderator reputation, or a globally portable trust score.

This audit does not approve direct source or schema transfer. The repository says no license has been chosen and all rights are reserved; confirm rights and ownership with the owner before copying or adapting code. Independently implementing selected concepts is a separate product and architecture decision, not blocked by the source-code transfer question. Recommend keeping this work separate for now; if OT later adopts a bounded mechanism, first evaluate a local, explainable moderation-evidence workflow. Do not apply this score model to TS or make a shared HAI-wide reputation service the default. This is an audit recommendation, not an ADR or authorization to implement.

DF-001 remains **DEFER**. Keep implementation at M/L pending a bounded product design; resolve rights/ownership separately before any direct source transfer. Keep validation at XL because any enforcement requires adversarial and affected-user evidence. No new RR implementation slice is justified by this audit.

## Reuse / adapt / rewrite / reject matrix

| Subsystem or concept | Disposition | Reason and boundary |
| --- | --- | --- |
| Direct reuse of any Retumbl subsystem | **REUSE: none approved** | License/ownership compatibility is unresolved, and no subsystem has passed the required abuse and runtime validation. |
| Durable score policy, decay, idempotency, and audit design | **ADAPT (concept only)** | Useful patterns for a future local policy engine, subject to OT scope, explicit explainability, data retention, appeal, and abuse requirements. Any independent implementation would be built in the owning OT service/library if approved. |
| Actor/domain distinction | **ADAPT (concept only)** | Avoids treating one actor's conduct as a host-wide verdict. Scores remain one instance's opinion; they must not become global identity attributes. OT would need community and local-authority semantics before choosing scope. |
| Report case aggregation and reversible recommendations | **ADAPT (concept only)** | Bounded evidence aggregation is more defensible than direct report-to-ban behavior, but current thresholds and automation are unvalidated. Keep decisions advisory until policy and human review are established. |
| Signed, expiring attestations with revocation and provenance | **ADAPT (concept only)** | Expiry and revocation support bounded evidence lifetimes. Cross-instance use still needs issuer accountability, retention limits, verification, privacy, and contest mechanisms. |
| Local vouch/boost as a score bypass | **REJECT as a default enforcement rule** | Vouches can reproduce popularity, exclusion, retaliation, and insider collusion. No user should receive access or credibility solely because of social endorsement. A narrow, transparent contextual signal would need a separate policy case. |
| `src/engine` simulation and seeded in-memory evaluator | **REJECT** | Random drops, mock state, and non-durable signals do not provide production behavior or evidence. |
| Direct reuse of Retumbl source or schema | **REJECT by this audit; rights decision required before transfer** | License and ownership are unresolved, and the data model is federation-specific. Independently implementing selected concepts is a separate product/architecture decision. No source was transferred. |
| Shared HAI reputation service or TS score model | **REJECT for current scope** | OT's and TS's authorization, community, locality, and moderation boundaries differ. A cross-product score would create an unjustified universal identity verdict. |

## Abuse and user-impact threat model

| Threat | Existing controls observed | Residual gap / required future evidence |
| --- | --- | --- |
| Brigading | Per-target reporter deduplication and influence caps; attestation thresholds require multiple issuer domains. | Coordinated but distinct reporters or issuers can still accumulate influence. Exercise synchronized bursts, target rotation, and appeals under realistic membership churn. |
| Sybil identities and collusion | Per-issuer/domain caps, shared-evidence hash damping, independent-domain thresholds, local-vouch age/budget/cooldown constraints. | Domain diversity is only a proxy for independence; a single actor can control multiple domains or mint distinct evidence hashes. Prove identity/issuer accountability or keep evidence advisory. |
| Retaliation and vendettas | Case evidence records provenance; penalties decay and operator blocks are explicit. | Reports expose reporter identifiers in stored records; no audited reporter confidentiality, safe contest flow, or retaliation response was established. Test targeted abuse and moderator access boundaries. |
| False or malicious reports/attestations | Signature checks, bounded confidence, expiry/revocation, case records, recommendations and reasoned admin controls. | Signatures prove issuer control, not truth. No independent adjudication or subject appeal is evidenced. Verify false-positive correction and full reversal through end-to-end flows. |
| Domain-wide collateral harm | Actor and domain scores are separate; domain penalties are smaller than actor penalties. | Domain score can still affect unrelated actors. Test shared-host innocent users, domain migration, and operator response before any enforcement. |
| Reputation persistence and privacy | Scores are locally stored and inspected through admin-gated APIs; evidence has expiry fields. | Retention, deletion, export, reporter/subject notice, and cross-instance provenance handling are unresolved. Define lifecycle and verify deletion/revocation semantics. |
| Opaque or irreversible automation | Recommendations are labeled reversible and penalties decay; admin endpoints support inspection and operator block. | The flag bridge applies penalties from aggregate reports; no affected-user appeal or clear notice path is established. A reason string and admin audit log do not alone make the process fair or tamper-proof. |

These gaps conflict with the HAI philosophy's requirements for transparent, proportionate moderation, understandable user control, and appeals where risk warrants them. The audit does not authorize automated reputation-based moderation claims.
