This slice addresses RR04-F02, F04, F05 and F06: explicit public intent in communities, safe post sharing, ordinary audience selection and profile-based Following Feed reads. It also covers durable post/comment image audience restrictions and the reproduced RR08 active-public-feed delivery failure. RR04-I03 retains the broader feed/privacy acceptance work. This report does not authorize a promotion, PR or deployment.

## Implemented behavior

- Personal posts default to public; ordinary authors can choose public or followers. Community posts default to members. Invalid audience values are rejected, updates preserve unrelated audience state, and clients cannot set the read-only `publicAudienceExplicit` marker.
- New public-community posts become globally public only when the author deliberately selects public. The public tab accepts personal public posts and explicitly public community posts. A private community's explicitly public post remains subject to approved membership at the server; anonymous and nonmember reads remain denied. Followers-only, member-only and legacy-intent community rows do not enter the public tab through realtime snapshots.
- Historical community posts with `visibility = public` have unknown author intent. A read-only inventory found 15 in public communities and 121 in private communities. They remain member-readable; they are not silently broadened. The additive marker defaults to false and no legacy rows were backfilled.
- Pending post and comment uploads derive durable audience restrictions from the selected parent context. Saved body URLs are checked against their actual assets; restrictions survive reference removal and current follow/member revocation. A commenter may attach their own image to another author's restricted post without transferring asset ownership. Unrelated third-party assets cannot be narrowed by a comment.
- Share creation checks the authenticated viewer's current access to the source, validates the requested audience, and prevents widening restricted content. Share reads require both share-audience access and current source access. Suppression, source restriction/deletion, unfollow and membership revocation remove visibility. Only the share owner can delete; expected 403/404 refusals cross the service boundary with status-bearing RPC errors.
- Following reads compare post profile IDs with followed profile IDs. Public, Following and Communities remain separate chronological feeds.
- Socket handlers wait for cookie-session authentication, and a disconnect while auth is pending prevents late registration, feed lookup and subscription. Post creation advances revisions for connected clients so pre-create feed snapshots do not overwrite newer state; this does not send post content to an unsubscribed client. The public tab filters generic realtime snapshots using the same audience rule as the public REST feed and applies that rule before any HTTP response resolves.

These attempts were diagnostic failures, not acceptance passes. Do not record storage key values in this report or test output.
