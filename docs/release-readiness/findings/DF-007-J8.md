# DF-007 J8 — Assets database and decrypted-media capture

**Status: locally verified owner component.** Assets can now capture every retained upload attributed to the fenced Profile identities, together with the account's actor-side and dependent-side guardian activity. The component is not registered in a module or exposed through RPC, and Authentication jobs do not consume it yet. Complete Assets integration, item 1, DF-007 and RR-11 remain open.

## Behavior and field scope

The reader validates the exact session/job lease before capture, before each delivered chunk and before completion. It consumes all J7 identity pages into a per-connection temporary table, then reads both Assets tables in one read-only repeatable-read transaction. A temporary table must be created before that transaction because PostgreSQL prohibits its creation inside a read-only transaction; inserts into the existing temporary table are allowed. UUID keyset pages include the all-zero UUID, have no preview row cap, and return bounded metadata. The service permits one capture at a time. Pending lifecycle rows, malformed relationships, unsupported data or exhausted budgets fail capture.

Asset output includes safe metadata and signature-classified, authenticated plaintext chunks with size and SHA-256 manifests. It includes unreferenced uploads. Storage paths, envelopes, configuration and audience ACL internals are omitted. The [field dispositions](../evidence/df-007/assets-owner-fields-j8.json) distinguish output, operational checks and redaction; this is not an assertion that every database column is serialized.

Media opens through the configured authenticated-storage API. Complete envelope authentication precedes plaintext reads. Reads enforce a 64 MiB per-file and 128 MiB per-capture plaintext budget, bounded chunks, cancellation and deterministic cleanup. Recognized signatures include PNG, JPEG, GIF, WebP, supported MP4 brands, QuickTime, WebM, WAV, OGG, MP3 and PDF. Other formats and the unsupported database-storage strategy fail capture. MIME validation is signature-level, not full codec or content-safety validation. Media is authenticated at read time; it is not a transaction-wide snapshot of the object store.

Guardian records retain both account roles while redacting counterpart user, profile and asset identifiers. The reader checks the current target Profile owner against the recorded dependent. That lookup is outside the Assets database snapshot and is not proof of historical provenance. List records use `*`; references to removed assets remain valid history. A present asset with contradictory profile linkage fails capture. Changed-field names are allowlisted; arbitrary payloads are not exported.

The terminal proof follows commit, temporary-table removal and connection release. Cleanup failure quarantines the reader and discards the dirty PostgreSQL connection through the installed TypeORM driver's error-release method. That version-specific seam must be reviewed on driver upgrades. No partial capture becomes a verified spool handle.

## Evidence

The scoped Assets production build and lint passed before the accepted private integration run. Eleven focused media tests and nine owner tests passed separately. Media tests used real encrypted local storage and ffmpeg-generated MP4/WebM fixtures, including tampered envelopes, wrong keys, unsupported adapters/strategy, budgets, abort and cleanup failure.

The enabled private PostgreSQL selection passed **four cases with zero skips**. Five actual Assets migrations ran on a fresh database with synchronization disabled. The fixture traversed 1,006 captured Profile IDs, exported 1,006 owned assets including the minimum UUID, verified actual PNG/MP4 bytes and hashes, projected five guardian activities and preserved counterpart rows. It also checked a later insert against the existing snapshot, a genuinely empty account, missing/corrupt media, pending rows, hostile names, contradictory relationships, lease loss, cancellation and actual dirty-connection eviction. Owning-table fingerprints before/after matched. Independent readback found zero asset/activity rows and temporary relations; the private container, network and volume were removed.

Authentication and Profile RPC responses are simulated in this component fixture; the database, owner reader, emitter, verifier, spools, encryption and local adapter are real. Only the unrelated Storage UUID dependency is substituted. J6 retains separate real Auth/Profile transport evidence. See the [receipt](../evidence/df-007/checkpoint-j8.json).

An initial precheck caught lint defects. The first PostgreSQL selection did not compile because a fixture case was outside its describe block. The next run passed three cases; its cancellation case checked resources before the owner producer had finished. The fixture now retains and awaits the owner promise on spool failure before requiring zero resources. These attempts remain separate in the receipt. The generic spool's prompt abort does not establish database cancellation; statements have local timeouts and downstream consumers must cooperate with abort signals.
