## Draft 5 — Account deletion and data export

### Proposed public section (unapproved)

> **Account and data requests**
>
> We do not currently have a supported profile or account-deletion process or data-export request process. [UNRESOLVED — do not replace this sentence with a request route or promise until the operator has approved and validated a process.]

### Proposed manual process to consider (not an existing process)

If the operator decides to offer a manual path before DF-007 implementation, first produce and validate a runbook covering all of the following:

1. A real monitored intake route and accountable operator; no route currently exists.
2. A safe way to establish the requester's account identity and authority without collecting unnecessary extra data.
3. Exact scope for account credentials/sessions, profile(s), user content, communities, messages, assets, permissions, payment records if any, and third-party/service dependencies.
4. Approved handling of content authored with other people, legal/operational holds, records that cannot be deleted, and any retained audit evidence.
5. A supported export format and completeness/readability checks if export is offered.
6. A retention/deletion schedule for every included record class, approved exceptions, and downstream/provider handling. No retention period is currently approved.
7. An approved acknowledgement/completion approach and any response times the operator can meet. No response deadline is currently supported.
8. A safe completion record and exact readback proving the promised outcome, plus negative tests for another person's data and unauthorized profile/scope access.
9. A rehearsal with disposable fixtures in an isolated environment, approved by service owners, before using any real account.

Do not use RR09-I04's retained synthetic global profile as a deletion test. RR11-I01 accepted the fail-closed profile-delete contract checkpoint, but no successful profile deletion or dependent-data lifecycle has been implemented or proven. A successful profile delete cannot substitute for the account-level DF-007 work.

### Options for owner selection (not recommendations)

| Area | Possible choice | Tradeoff to review |
| --- | --- | --- |
| Availability | State that no supported process currently exists and defer claims, or implement a bounded manual path after a tested runbook is approved. | Deferral avoids implying an unavailable service; a manual path can provide earlier user control but requires identity checks, cross-service scope, trained ownership, evidence, and retention decisions. |
| Scope | Limit any interim manual path to specific record classes, or wait for the DF-007 account-wide inventory and workflow. | Narrow scope may be achievable sooner but must be described precisely; broader scope is clearer for users but materially more work to implement and prove. |
| Export format | Defer export, or define a tested machine-readable/human-readable format as part of a separately bounded plan. | Deferral avoids a misleading incomplete export; a format helps portability but requires completeness, redaction, and safe-readback criteria. No format is selected here. |
| Retention | Approve a category-specific schedule, or hold publication until each service/provider dependency is mapped. | Specific schedules improve clarity but require proof across backups, logs, and providers; waiting avoids unsupported periods. No duration is proposed. |
