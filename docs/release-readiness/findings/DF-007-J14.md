# DF-007 J14 — UUID case coverage in existing owners

**Status: locally verified component repair.** Profile, Assets and Videos now include canonical UUID owner keys stored with uppercase letters in varchar columns. The old exact-text predicates could omit those rows before validation saw them. Authentication's reviewed owner keys are native UUID columns and needed no repair. DF-007 and RR-11 remain open.

## Behavior

Profile folds account predicates in current Profile/Timeline capture, retained Goal/Project capture, relationship checks and long-text/media rereads. Validated owner IDs serialize in canonical lowercase. Assets folds profile scope joins for metadata, media and HLS references, plus guardian activity account selectors. Its media cursor, comparison and ordering all use the same folded profile key and native Asset UUID. Videos folds account/profile selectors across its seven sources while preserving relationship checks and creator redaction.

This changes UUID identity handling. Native UUID relations, freeform strings, app identifiers, counterpart boundaries and byte content keep their existing semantics. It does not broaden ownership to arbitrary noncanonical strings. A peer source review found no blocker in the media-owner predicates or Assets cursor.

## Evidence

Twenty-five focused tests passed: three current Profile owner, seven legacy reader, ten Assets owner and five Videos owner cases. All three production builds and owning lint checks passed.

Fresh private PostgreSQL selections passed **five cases in three separate runs**: Profile two, Assets two and Videos one. Twelve unchanged Assets/Videos cases were unselected. The fixtures use UUIDs containing letters and assert that stored values actually differ from their lowercase form.

Profile verified uppercase Profile, Timeline, Goal and Project keys, full text and inline media rereads, and counterpart preservation after its three actual migrations. Assets verified encrypted HLS/TS/MP4 bytes, original hashes, offline decoding and guardian account roles after five migrations. Its 201-row fixture stores both spellings for each canonical profile, asserts two distinct stored variants, and verifies the exact media manifest ID set, sizes/hashes and multiple keyset pages. Videos verified all seven sources, 1,006 identities/channels/videos, uppercase account/profile actors, personal foreign-target views and counterpart privacy after three migrations.

Independent readback found zero fixture rows in all fourteen tables and no temporary relations. Owner/media spool checks and private teardown passed, leaving no private containers or volumes. See the [receipt](../evidence/df-007/checkpoint-j14.json).

An initial Profile launcher reached PostgreSQL's temporary initialization socket before the fixture database existed. The launcher now requires a successful query over TCP to the exact private database; no product code changed for that retry. An initial passing Assets run lacked its intended mixed-case seed because both branch parameters were uppercase. The corrected fixture explicitly checks both stored variants and passed the final selection. Earlier evidence remains separate.

These are database/media component checks with the existing mocked Auth/Profile RPC boundaries. Live transport, browser, remote CI and production qualification were not run for this repair.
