## How to use the register

Execute in table order, respecting explicit dependencies. `ACTIVE` means work has begun, not acceptance. All other rows are `PLANNED` unless a finding records otherwise. Mapping can run alongside an independent implementation; code and acceptance remain ordered. Each completed slice gets a finding, machine-readable receipt and synchronized master/execution/completion status.

Each slice must own named files and one bounded result before implementation. If a domain capture cannot fit that boundary, declare its source-specific child IDs before writing code; do not quietly expand it or claim the parent accepted. Unknown ownership, missing handlers and inaccessible stores are blockers, never empty-data success. Existing previews remain compatible and explicitly partial. No new retention exceptions are authorized. Never delete another person's content; preserve conversations with the approved deleted-account placeholders. Do not retain credentials in operation ledgers.

**Common pre-E2E gate:** inspect affected Nx/CI targets; run the narrow meaningful regression, changed contracts' checks, owning production build/lint and affected E2E lint. Run API generation/drift checks when the API schema changes. Use Node 24, `NX_DAEMON=false`, `NX_ISOLATE_PLUGINS=false`, and private runtime fixtures. Schema changes require the owning Nx migration-generation target, reviewed SQL, fresh-database migration run and migration validation. Record caches, skips and checks not run. Do not repeat unchanged accepted tests without a new concern.

**Common runtime gate:** actual owning database/service, positive and negative authorization, multi-page owned data, foreign-account exclusion, failure/retry/lease/restart where applicable, independent readback, source/image identity and exact private teardown. Source presence or units alone do not close an owner.
